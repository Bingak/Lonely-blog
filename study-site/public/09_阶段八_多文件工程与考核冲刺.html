1. 本节目标与前置知识

目标：

  1. 真正吃透声明与定义的区别：声明是「我保证有这个东西」，定义是「东西在这里，存储/代码由我出」。
  2. 会把一个程序拆成 .h 与 .c：头文件只放公开接口，源文件负责实现，知道什么该放、什么绝对不能放。
  3. 能默写头文件守卫（#ifndef / #define / #endif），并解释它为什么只能防「同一个编译单元内的重复包含」。
  4. 掌握 extern 与 static 的跨文件用法，理解外部链接/内部链接：能用 extern 共享变量，用 static 把私有函数和私有状态关进当前 .c，不污染全局符号表。
  5. 建立编译单元（translation unit）与链接器（linker）的心智模型，能独立诊断 undefined reference、multiple definition、implicit declaration 三兄弟。
  6. 掌握模块化拆分方法：按职责切、依赖单向、接口最小；能画出「谁包含谁、谁链接谁」的结构图。
  7. 掌握菜单-登录类程序的结构模式：状态机 + 函数分派 + 输入清洗；知道登录门禁应该放在哪一层。
  8. 会写最小可用 Makefile，理解目标、依赖、命令、.PHONY 与增量编译；对 CMake 建立概念级认识。
  9. 按规范独立完成考核任务，通过自查清单与 PDF 中的登录测试，提交 Gitee——本阶段只给地图，不给你答案。

前置： 阶段三你学过「原型声明」，当时只是一行 int is_prime(int n);；阶段一你学过「预处理→编译→汇编→链接」四步流水线，当时只处理一个 .c。本阶段就是把这两件事放到多文件场景里兑现：原型声明是文件之间的合同，链接器是合同的执行者。 如果这两处还有一点模糊，先回去看阶段三 §3 和阶段一 §3，再往下读。

2. 场景引入：800 行之后，你撞上了一堵看不见的墙

阶段七结束那天，你觉得自己已经「会 C 了」：分支、循环、函数、数组、字符串、指针、结构体、位运算，零件齐了。考核任务看起来也不复杂——一个结构体存个人信息，一个登录门禁，一个菜单循环，改改姓名、学号、性别、身高，最后退出。你打开 main.c，从第一行开始写。

一开始很顺。结构体定义、几个字符串函数、登录校验、菜单打印、修改函数，全都塞进同一个文件。写到三百行，你开始用注释划分区域；写到六百行，找一个函数要滚三次滚轮；写到八百行，你改了一个菜单提示语，按下编译，然后等——整个文件从头再编译一遍。你安慰自己：「能跑就行。」

直到某一天，你想把登录部分拆到另一个文件。灾难开始了：

  • 你把 check_login 搬到另一个源文件，编译 main.c 时它说 implicit declaration of function 'check_login'；
  • 你补上声明，链接时它说 undefined reference to 'check_login'——因为你只编译了 main.c，忘了把那个新文件加进命令；
  • 你把 current_user 定义在头文件里，两个 .c 都包含它，链接器冷冷地说 multiple definition of 'current_user'；
  • 你给头文件加上守卫，重复包含的错误消失了，但 multiple definition 依然在——你开始怀疑「守卫是不是假的」；
  • 你写了一个 Makefile，命令行明明对齐了，mingw32-make 却只回你一句 missing separator. Stop.；
  • 最气的是，有些错误不是代码写错了，而是文件没放对、头文件没包含、编译命令少了一个 .c、Makefile 少了一个依赖。你盯着代码看半小时，真正的问题在「工程」里。

这不是 C 突然变难了，而是你第一次遇到了工程问题。 单文件时，所有函数住在同一间屋子里，喊一嗓子就能听见；多文件时，每个 .c 是一个独立车间，.h 是接口说明书，链接器是总装线。车间之间不能靠喊，只能靠合同；总装线不认你的注释，只认符号。

考核任务明确要求「模块化」，这不是装饰性的加分项，而是及格线。它考的不只是你会不会写 struct，而是：你能不能让五六个文件在一个工程里各司其职、还能一起编译出一个干净的可执行文件。

本阶段给你四件工具：合同（声明与头文件）、门锁（头文件守卫与 static）、总装图（编译单元与链接）、自动流水线（Makefile）。学会它们，你才算从「写程序的人」变成「搭工程的人」。

3. 核心概念一：声明与定义——阶段三那句老话，今天才真正落地

3.1 一句话版本

阶段三我们说过：「声明说有，定义给实现。」 当时你只在同一个 .c 里用，感受不深。现在把这句话放大到多文件：

项目 声明（declaration） 定义（definition）
函数 int add(int a, int b); 原型，分号结尾，没有函数体 int add(int a, int b) { return a + b; } 有函数体
变量 extern int g_total; 告诉编译器「有这个变量」 int g_total = 0; 真正分配存储
是否产生存储/代码 不产生 产生
能否重复 可以重复（只要类型一致） 同一个外部符号只能有一份
放在哪 头文件、调用前的源文件 且仅在一个 .c 里

声明是承诺，定义是兑现。 头文件是承诺书，.c 是兑现处。承诺书可以复印很多份，兑现处只能有一个——这就是多文件工程最朴素的一条纪律。

3.2 函数原型：把「怎么调用」提前告诉编译器

编译器是一次只处理一个 .c 的。它在 main.c 里看到 add(3, 4) 时，必须知道：add 是个函数、要几个参数、参数是什么类型、返回什么类型。否则它没法检查实参、没法生成正确的调用代码。

原型就是干这个的：

int add(int a, int b);   /* 原型：分号结尾，没有函数体 */

参数名 a、b 可以省略，写成 int add(int, int); 也合法；但建议保留，因为它是给读代码的人看的文档。没有参数就写 (void)：int get_count(void);。不要写成 int get_count();——在 C99 里这表示「参数情况未指定」，不是一个严格的「无参数」原型，容易埋坑。

函数定义则是：

int add(int a, int b)
{
    return a + b;
}

定义只能有一份。你可以把原型抄十遍，编译器不生气；但把函数体抄两遍，链接器就会生气。

3.3 变量：extern 是「借条」，定义才是「房子」

变量比函数更容易出事。看这两行：

extern int g_total;   /* 声明：g_total 在别处，这里不分配存储 */
int g_total = 0;      /* 定义：这里真的有一块存储，初始值为 0 */

extern 的意思是「这个变量已经存在，只是不在当前文件里」。它不分配内存，只告诉编译器「这个名字可以用，类型是 int」。真正的存储由某一个 .c 里的定义提供。

在文件作用域写 int g_total;（没有 extern）通常也会被当作定义，编译器会为它分配存储。所以千万不要把 int g_total; 放进头文件：头文件被几个 .c 包含，就会在几个编译单元里各定义一份，链接器看到多个同名强符号，直接报 multiple definition。

还有一个容易忽略的细节：extern int g_total = 0; 虽然写了 extern，但带初始化，仍然是定义。头文件里不要出现任何带初始化的变量定义，这是最省心的判断法。

严谨补一句：文件作用域的 int g; 在没有初始化时叫暂定定义（tentative definition），同一个编译单元里重复出现可能被编译器合并；但跨编译单元各写一份，仍然是多个外部定义，链接器会报错。初学阶段不要研究这个边缘规则，按「头文件 extern、一个 .c 定义」做就永远不会错。

3.4 看一遍 01_decl_vs_def.c

配套文件把「原型可以重复」「extern 声明」「定义只有一份」放在同一个程序里，先跑一遍：

/* 01_decl_vs_def.c —— 阶段八：声明、定义、原型与 extern 变量
 * 编译：gcc -Wall -Wextra -std=c99 -g 01_decl_vs_def.c -o 01_decl_vs_def.exe
 * 说明：演示“声明可以重复，定义只能一次”，底部保留 implicit declaration 对照实验。
 */
#include <stdio.h>

/* ① 函数原型：声明“有这样一个函数”，分号结尾，没有函数体 */
int add(int a, int b);
int add(int a, int b);   /* 声明可以重复，编译器不报错 */

/* ② 全局变量：extern 是声明，不分配存储；下面一行才是定义 */
extern int g_total;
int g_total = 0;         /* 整个程序里这个定义只能有一处 */

/* ③ 函数定义：真正生成代码的地方，只能有一处 */
int add(int a, int b)
{
    return a + b;
}

void bump_total(int n)
{
    g_total += n;
}

int main(void)
{
    int x = 3, y = 4;

    printf("add(%d, %d) = %d\n", x, y, add(x, y));
    bump_total(add(x, y));
    printf("g_total = %d\n", g_total);

    /* 隐式声明对照实验（默认注释，取消注释后重新编译）：
     * int z = undeclared_helper(5);
     * printf("%d\n", z);
     * 在较老的 GCC 上会看到：
     * warning: implicit declaration of function 'undeclared_helper'
     * 在本机 GCC 16.2 上会直接看到 error: implicit declaration...
     * 两者本质相同：调用点没有可见的原型。
     */
    return 0;
}

预期输出：

add(3, 4) = 7
g_total = 7

这份代码故意把 extern int g_total; 和 int g_total = 0; 放在同一个文件里，只为了让你看见两种写法的区别。真实工程里，extern 那行要搬进头文件，定义那行留在唯一的 .c 里——这就是跨文件版的同一件事。

3.5 为什么声明可以重复，定义不行？

因为编译器一次只看见一个编译单元。main.c 需要知道 add 长什么样，所以它读一遍原型就够了；calc.c 也需要知道，所以它也读一遍原型。两份原型在各自的编译单元里独立存在，互不冲突。

但定义会生成符号（函数代码或变量存储）。链接器把多个 .o 拼在一起时，同一个外部符号出现两份定义，它不知道该用哪一份，只能报错。声明是给编译器的，定义是给链接器的。 这句话请记到错题本第一页。

4. 核心概念二：头文件——只放「菜单」，不放「厨房」

4.1 头文件到底是什么

#include "calc.h" 不是「导入一个模块」，而是预处理阶段的文本复制粘贴。预处理器把 calc.h 的内容原样倒进 calc.c，然后编译器才开始看代码。所以头文件不是「另一个程序」，它只是一段被反复粘贴的公共文本。

这段公共文本应该是什么？接口。也就是：「别人要使用我这个模块，必须知道的东西。」用餐厅打比方：头文件是菜单，.c 是厨房。客人只需要看菜单点菜，不需要进厨房看你怎么切菜。

4.2 该放什么，不该放什么

放在头文件里 原因
函数原型 调用者需要知道参数和返回值
extern 变量声明 调用者需要知道变量存在及类型
结构体、枚举、typedef 定义 调用者要按这个布局创建或访问数据
宏、常量 调用者和实现需要共享同一套约定
该头文件自身需要的标准头 让头文件「自给自足」，不依赖包含顺序
不要放在头文件里 后果
函数定义（函数体） 每个包含它的 .c 都生成一份定义，链接时 multiple definition
变量定义（int g;、int g = 0;） 同上，多个 .o 各有一份存储
main 函数 一个程序只能有一个入口
只在本模块内部使用的辅助函数 暴露了实现细节；应放在 .c 里并加 static
#include "xxx.c" 把实现文件当文本倒进来，几乎必然重复定义，还会破坏独立编译

一个常见的例外是 static inline 函数：C99 允许在头文件里定义 static inline 小函数，让每个编译单元各有一份内联副本。初学阶段先不碰它，记住默认纪律：头文件只放接口需要的东西（声明、类型、宏），函数体回 .c。

4.3 头文件要「自给自足」

一个合格的头文件，应该能被单独包含而编译通过。比如：

  • 头文件里用了 size_t，就自己 #include <stddef.h>，不要赌调用者先包含了它；
  • 头文件里用了 FILE *，就自己 #include <stdio.h>；
  • 头文件里用了 int32_t，就自己 #include <stdint.h>。

为什么？因为调用者的包含顺序你控制不了。今天 main.c 先包含 <stdio.h> 再包含你的头文件，编译通过；明天另一个 .c 只包含你的头文件，就报 unknown type name 'size_t'。头文件不能依赖「别人应该先包含什么」这种默契。

一个很实用的自检法：新建一个临时 .c，里面只写一行 #include "calc.h"，编译它。能过，说明头文件自足；过不了，就补它缺的包含。

4.4 .c 要包含自己的头文件

每个模块的 .c 第一件事，应该是包含自己的 .h：

#include "calc.h"
#include <stddef.h>

这不是形式主义。它让编译器拿 .h 里的原型去核对 .c 里的定义：参数类型不一致、返回类型不一致、函数名拼错，编译阶段就能抓到。如果你不包含自己的头文件，声明和定义可能各说各话，编译器不报错，链接器也不报错（它只认名字），最后运行时才以「参数传错、返回值乱码」的方式爆炸。

头文件是合同，.c 是签字方。签字之前，先把自己的合同读一遍。

4.5 永远不要 #include "calc.c"

有些初学者为了「让 main 看见 calc 的函数」，会在 main.c 里写 #include "calc.c"。这在单文件思维里似乎很方便，实际是把两个实现文件硬拼成一个编译单元：

  • 如果 main.c 和别的文件都包含了 calc.c，calc_add 就会有重复定义；
  • calc.c 里的 static 变量会被复制进每个包含者，状态各自独立；
  • 你再也无法单独编译 calc.c，Makefile 的依赖关系也全乱了。

正确做法永远是：.c 编译成 .o，.h 提供声明，链接器把 .o 拼起来。 不要用 #include 走捷径。

5. 核心概念三：头文件守卫——给每个头文件上锁

5.1 为什么会被包含两次

头文件被包含两次，比你想的更常见。假设 main.c 这样写：

main.c
  ├── #include "student.h"        → struct Student 第一次定义
  └── #include "另一个头文件"
        └── #include "student.h"  → struct Student 第二次定义 → 编译错误

你只写了一行 #include "student.h"，但另一个头文件内部也包含了它。预处理器不管重复，照样复制粘贴。于是同一个结构体在同一个编译单元里被定义了两次，编译器报 redefinition of 'struct Student' 或 conflicting types。

函数原型重复没关系，结构体、枚举、typedef 重复定义不行——类型不能有两份不同的定义。这就是头文件守卫要解决的问题。

5.2 三行锁：#ifndef / #define / #endif

#ifndef HEADER_GUARD_DEMO_H
#define HEADER_GUARD_DEMO_H

/* 这里放头文件的全部内容 */

#endif /* HEADER_GUARD_DEMO_H */

逻辑非常朴素：

  1. 第一次包含时，HEADER_GUARD_DEMO_H 还没定义，#ifndef 为真，进入内容区；
  2. 进入后立刻 #define HEADER_GUARD_DEMO_H，给这次包含打上「已读」标记；
  3. 第二次包含时，宏已经定义，#ifndef 为假，整段内容被跳过。

宏名要唯一，通常用「项目/模块名 + _H」全大写。不要用 _ 开头再加一个大写字母（比如 _CALC_H），这类名字在 C 标准里是保留给实现的，容易撞车。#endif 后面写注释是好习惯，长头文件里能一眼看出这行闭合的是哪个守卫。

5.3 看一遍 02_header_guard.h 与 02_header_guard.c

02_header_guard.h：

/* 02_header_guard.h —— 头文件守卫的最小完整例子 */
#ifndef HEADER_GUARD_DEMO_H
#define HEADER_GUARD_DEMO_H

#define DEMO_NAME_MAX 16

typedef struct {
    int id;
    char name[DEMO_NAME_MAX];
} DemoItem;

int demo_add(int a, int b);

#endif /* HEADER_GUARD_DEMO_H */

02_header_guard.c：

/* 02_header_guard.c —— 同一个头文件被包含两次，守卫保证不重复展开 */
#include <stdio.h>
#include "02_header_guard.h"
#include "02_header_guard.h"   /* 第二次包含：守卫让这段内容不再展开 */

int demo_add(int a, int b)
{
    return a + b;
}

int main(void)
{
    DemoItem item = {1, "guard"};

    printf("item = %d/%s\n", item.id, item.name);
    printf("demo_add(2, 3) = %d\n", demo_add(2, 3));
    return 0;
}

预期输出：

item = 1/guard
demo_add(2, 3) = 5

把 02_header_guard.h 复制一份，注释掉三行守卫，再编译一次，你会亲眼看到 redefinition。先看它坏，再看它好，比背定义有效十倍。

5.4 守卫的边界：它只管一个编译单元

这是本阶段最容易被误解的一点，请画重点：

头文件守卫只能防止「同一个编译单元内重复包含」，不能防止「多个编译单元各定义一份」。

为什么？因为每个 .c 被预处理时，都是从零开始的。main.c 的预处理器定义了 CALC_H，这只存在于 main.c 的预处理过程里；calc.c 的预处理器根本不知道 main.c 发生过什么，它也会重新定义一次。于是如果头文件里有 int g_score = 0;，两个 .c 各得到一份定义，守卫一点忙都帮不上。

所以正确的组合拳是：

  • 守卫 → 解决同一编译单元内的重复包含；
  • extern 声明 + 单个 .c 定义 → 解决跨编译单元的重复定义；
  • static → 把不需要对外的东西藏进当前编译单元。

守卫不是万能锁，它只是门上的「防重复进入」装置。真正的存储管理，要靠声明/定义和链接属性。

5.5 #pragma once 要不要用

#pragma once 是编译器扩展，几乎所有主流编译器都支持，写起来短。但它不是 C 标准，遇到特殊构建环境可能失效。课程作业和考核统一用标准守卫；看到别人的代码用 #pragma once，知道它是什么意思即可，不必跟风。

6. 核心概念四：extern——「这个东西在别处」

6.1 外部链接：名字是全局的

C 的普通全局变量和普通函数，默认具有外部链接（external linkage）：它们的名字会进入目标文件的符号表，链接器在其他 .o 里也能找到。extern 就是用来声明一个具有外部链接、但定义在别处的名字。

对函数来说，extern 通常是可省的：

int calc_add(int a, int b);          /* 默认就是外部链接 */
extern int calc_add(int a, int b);   /* 等价，写不写 extern 都行 */

对变量来说，extern 不能省：

extern int g_total;   /* 声明：别处有定义 */
int g_total = 0;      /* 定义：这里才是真身 */

6.2 正确的跨文件姿势

把 01_decl_vs_def.c 里的那两行拆到工程里，就是下面这个模式（这里不新增配套文件，只描述动作）：

  • 在模块的 .h 里写 extern int g_total; 和 void bump_total(int n);；
  • 在模块的 .c 里写 int g_total = 0; 和 void bump_total(int n) { g_total += n; }；
  • 在 main.c 里包含对应的头文件，然后直接使用 g_total 和 bump_total。

编译时，main.c 只看到 extern 声明，生成一个「未定义符号」的引用；该模块的 .c 生成真正的定义；链接器把引用和定义接上。头文件负责让编译器闭嘴，.c 负责让链接器闭嘴。

6.3 为什么全局变量要少用

extern 很好用，但它是「隐形的数据通道」。函数签名上看不出它依赖 g_total，测试时也很难把状态清干净。两个模块都改同一个全局变量，出了 bug 你都不知道是谁改的。

考核里如果确实需要保存「当前登录用户」这类跨函数状态，可以用一个明确的模块状态，或者把结构体指针传进函数。能用参数和返回值说清的数据流，不要用全局变量走暗道。 extern 是工具，不是设计目标。

6.4 extern 数组的小尾巴

如果头文件要声明一个数组，可以写：

extern int g_scores[];   /* 声明：长度在定义处给出 */

定义处必须给出完整数组：

int g_scores[10];        /* 定义：10 个 int 的存储 */

数组声明不写长度是合法的（不完整类型），但定义必须完整。初学阶段如果记不住，就老老实实把数组封装进结构体，用函数传指针和长度——这也是更安全的工程习惯。

7. 核心概念五：static——把名字关进文件里

7.1 三种「链接属性」先分清

写法 链接属性 谁能看见
普通全局变量 / 普通函数 外部链接 所有 .c，链接器可解析
文件作用域的 static 变量/函数 内部链接 只有当前 .c（当前编译单元）
函数内的局部变量 无链接 只有当前函数作用域

static 放在文件作用域（函数外面）时，含义是「这个符号只属于本编译单元，不导出给链接器」。它和「函数内的 static 局部变量」是两件事：后者讲的是生存期（程序运行期间一直存在），前者讲的是可见性（别的文件看不见）。初学阶段先把这两个概念分开，不要混成一句「static 就是静态」。

7.2 看一遍 03_static_internal.c

/* 03_static_internal.c —— 文件作用域 static：内部链接，只属于当前编译单元
 * 编译：gcc -Wall -Wextra -std=c99 -g 03_static_internal.c -o 03_static_internal.exe
 */
#include <stdio.h>

/* 文件作用域的 static 变量：其他 .c 文件既看不见，也无法 extern 到它 */
static int s_score_count = 0;

/* 文件作用域的 static 函数：本文件的私人助手，不导出符号 */
static int clamp_score(int score)
{
    if (score < 0) {
        return 0;
    }
    if (score > 100) {
        return 100;
    }
    return score;
}

/* 对外接口：其他 .c 只能通过这个函数间接使用 clamp_score */
int record_score(int score)
{
    s_score_count++;
    return clamp_score(score);
}

int get_score_count(void)
{
    return s_score_count;
}

int main(void)
{
    printf("record_score(120) = %d\n", record_score(120));  /* 100 */
    printf("record_score(-5)  = %d\n", record_score(-5));   /* 0 */
    printf("count = %d\n", get_score_count());              /* 2 */
    return 0;
}

预期输出：

record_score(120) = 100
record_score(-5)  = 0
count = 2

record_score 和 get_score_count 是公开接口，其他 .c 可以调用；s_score_count 和 clamp_score 被 static 关在本文件里。别的 .c 就算写 extern int s_score_count;，链接时也只会得到 undefined reference——因为链接器根本看不到这个内部符号。

7.3 文件作用域 static 的三个好处

  1. 防重名：两个模块都可以有自己的 static int s_count; 或 static void helper(void);，链接器不会打架；
  2. 隐藏实现：头文件里不用暴露辅助函数，接口更干净；
  3. 减少误用：别人无法绕过你的公开接口直接改内部状态。

可以把 static 理解成「这个车间内部的工具，不出厂」。工具留在车间里，总装线不需要知道它。

7.4 函数内的 static：另一件事

void tick(void)
{
    static int count = 0;   /* 只初始化一次，函数返回后仍然活着 */
    count++;
    printf("tick = %d\n", count);
}

每次调用 tick，count 都保留上一次的值。它没有链接属性，只影响生存期。用它可以做「调用次数统计」「只初始化一次」这类事，但要注意：它让函数带上了隐藏状态，测试时不好重置。能用参数传状态，就别用 static 局部变量藏状态。

7.5 static 和头文件：不要乱放

如果你在头文件里写：

static int helper(int x) { return x + 1; }

每个包含该头文件的 .c 都会得到自己的一份 helper。它们互不共享，代码体积还会膨胀。更糟的是，你在头文件里声明 static int helper(int); 却没有定义，包含它的 .c 会得到「声明了 static 但没定义」的警告或错误。

规则很简单：

  • 公开函数：在 .h 里放原型，在 .c 里定义，不加 static；
  • 私有函数：只在 .c 里定义，加 static，头文件里连提都不要提；
  • 头文件里不要放普通函数定义，也不要放 static 函数定义（static inline 是例外，等以后再说）。

默认给函数加 static，除非你确定它是这个模块的公开接口。 这是「最小暴露原则」在 C 里的具体写法。

8. 核心概念六：编译单元与链接——编译器一次只看见一个 .c

8.1 编译单元是什么

把 main.c 和它包含的所有头文件放在一起，经过预处理，得到一份巨大的 .c 文本；这份文本就是一个编译单元（translation unit，简称 TU）。编译器把这个 TU 翻译成一个目标文件 main.o。

main.c ──include──> calc.h
calc.c ──include──> calc.h
   │                    │
   ▼                    ▼
main.o               calc.o
   └────── link ───────┘
            ▼
       calc_demo.exe

关键事实：

  1. .h 不会被单独编译成 .o。它只是被复制进包含它的 .c；
  2. 每个 .c 独立编译。编译 main.c 时，编译器完全不知道 calc.c 里有什么；
  3. 链接器负责拼装。它把多个 .o 和标准库放在一起，解析符号引用，生成 .exe；
  4. #include 发生在链接之前。它只解决「声明可见」，不解决「实现在哪」。

8.2 编译器与链接器的分工

阶段 谁在工作 它看什么 它关心什么
预处理 预处理器 #include、#define 文本替换、展开头文件
编译 编译器 一个编译单元 语法、类型、原型是否可见
汇编 汇编器 汇编代码 生成机器码 .o
链接 链接器 多个 .o + 库 符号是否有定义、是否重复

编译器看到 calc_add(1, 2) 时，只要之前有原型，它就放心生成调用代码；它不检查 calc_add 到底在哪个 .o 里。链接器看到 main.o 里有一个「未定义的 calc_add」，就去其他 .o 和库里找；找到就接上，找不到就报 undefined reference。

链接器只认名字，不认参数类型。 这句话很重要：如果你在头文件里写 int calc_add(int, int);，在 calc.c 里却定义成 double calc_add(double, double)，编译器在 calc.c 里会报冲突（因为它包含了自己的头文件）；但如果某个调用者没包含新头文件，链接器仍可能把名字接上，运行时参数和返回值的解释全错。头文件是唯一的合同，改签名必须同步改头文件和所有调用者。

8.3 错误三兄弟：undefined、multiple、implicit

8.3.1 undefined reference to 'calc_add'

症状： 编译都过了，最后链接时出现 undefined reference to 'calc_add'。

本质： 有人引用了这个符号，但链接器在所有 .o 和库里都找不到它的定义。

常见原因：

  • 编译命令漏了实现文件：只写了 gcc main.c -o app.exe，没带 calc.c；
  • 函数只在头文件里声明了，.c 里忘了写函数体；
  • 函数名拼写不一致：声明 calc_add，定义 calc_ad；
  • 函数在另一个 .c 里被 static 了，链接器看不见；
  • 条件编译导致定义被 #if 排除了。

药方： 先看「谁引用了它、谁应该定义它」，再把该 .c 加入编译命令；如果是 static 导致的，要么把接口改成公开函数，要么把调用移到同一个 .c。

8.3.2 multiple definition of 'g_score'

症状： 链接器说某个符号「first defined here」，然后 multiple definition。

本质： 同一个外部符号在多个 .o 里都有定义，链接器不知道选哪个。

最常见的原因： 把变量定义或函数体写进了头文件。头文件被两个 .c 包含，就产生两份定义。

药方：

  • 变量：头文件里改成 extern 声明，定义只留在一个 .c；
  • 函数：头文件只留原型，函数体搬回 .c；
  • 检查有没有 #include "xxx.c" 这种操作。

注意： 头文件守卫不能修复这个错误。守卫只保证同一个 TU 不重复展开，不能阻止两个 TU 各自定义一份。

8.3.3 implicit declaration of function 'str_len'

症状： 调用函数时，编译器说「隐式声明」。较老的 GCC 在 -Wall 下给警告，本机 GCC 16.2 直接给 error。

本质： 调用点之前没有看见这个函数的原型。C99 已经取消了「隐式声明返回 int」的合法地位，编译器只能根据旧规则猜，或者直接拒绝。

常见原因：

  • 忘了包含字符串工具的头文件；
  • 头文件里忘了写这个函数的原型；
  • 函数定义在调用之后，而调用前没有原型；
  • 函数名或头文件名拼写错误，结果包含的头文件里没有这个原型。

为什么危险： 如果编译器按旧规则猜成「返回 int」，而你实际函数返回 char * 或 struct *，返回值可能被截断成 32 位，指针高位丢失，运行时崩溃。隐式声明不是「能用就行」，是「编译器在替你猜，而它很可能猜错」。

药方： 在头文件里写原型，在调用者里包含头文件；确保 -Wall -Wextra 下零警告。新版 GCC 把它当 error 其实是好事——它在帮你把炸弹提前拆掉。

8.4 三兄弟的记忆法

  • undefined reference = 有人要，没人给；
  • multiple definition = 两个人抢着给；
  • implicit declaration = 用之前没人告诉编译器它长什么样。

遇到它们，先问一句：这是编译期还是链接期？ 编译期的问题去查头文件、原型、类型；链接期的问题去查源文件清单、定义、static、重复包含。方向对了，解决只是几分钟的事。

9. 核心概念七：模块化拆分——按职责切，不按行数切

9.1 拆分的三条原则

第一，按职责拆，不按行数拆。 「这个文件 300 行了，切成两个」是裁纸，不是设计。正确的问法是：「这个模块为什么存在？它负责哪一类变化？」登录逻辑、个人信息、菜单显示、字符串工具，它们变化的原因不同，应该分开。

第二，依赖单向。 入口层可以依赖业务层，业务层可以依赖工具层，工具层不要反过来依赖菜单。依赖成环（A 包含 B，B 又包含 A）会让头文件互相撕扯，编译顺序怎么排都不对。真遇到共享类型，抽一个只放类型的小头文件，让两边都依赖它。

第三，接口最小。 头文件只暴露调用者真正需要的东西。辅助函数用 static 藏在 .c 里，内部状态不要做成全局变量。接口越小，改实现时越不容易波及别人。

9.2 一个最小多文件工程：04_project_demo\

目录结构：

04_project_demo\
├── main.c      程序入口，负责调用和演示
├── calc.h      计算模块的公开接口
├── calc.c      计算模块的实现
└── Makefile    构建脚本

calc.h：

/* calc.h —— 计算模块的公开接口：只放声明，不放实现 */
#ifndef CALC_H
#define CALC_H

int calc_add(int a, int b);
int calc_sub(int a, int b);
int calc_mul(int a, int b);

/* 除法：成功返回 0，并通过 out 带回商；除数为 0 或 out 为空返回 -1 */
int calc_div(int a, int b, int *out);

#endif /* CALC_H */

calc.c：

/* calc.c —— 计算模块的实现：包含自己的头文件，保证声明与定义一致 */
#include "calc.h"
#include <stddef.h>

int calc_add(int a, int b)
{
    return a + b;
}

int calc_sub(int a, int b)
{
    return a - b;
}

int calc_mul(int a, int b)
{
    return a * b;
}

int calc_div(int a, int b, int *out)
{
    if (out == NULL) {
        return -1;
    }
    if (b == 0) {
        return -1;
    }
    *out = a / b;
    return 0;
}

main.c：

/* main.c —— 程序入口：只负责调用 calc 模块，不重复实现计算 */
#include <stdio.h>
#include "calc.h"

int main(void)
{
    int quotient = 0;

    printf("3 + 4 = %d\n", calc_add(3, 4));
    printf("3 - 4 = %d\n", calc_sub(3, 4));
    printf("3 * 4 = %d\n", calc_mul(3, 4));

    if (calc_div(7, 2, &quotient) == 0) {
        printf("7 / 2 = %d\n", quotient);
    } else {
        printf("7 / 2 failed\n");
    }

    if (calc_div(1, 0, &quotient) != 0) {
        printf("1 / 0 rejected\n");
    }
    return 0;
}

预期输出：

3 - 4 = -1
3 * 4 = 12
7 / 2 = 3
1 / 0 rejected

9.3 谁包含谁、谁链接谁

main.c ──#include──> calc.h <──#include── calc.c
   │                                      │
   ▼                                      ▼
main.o                                 calc.o
   └────────────── link ─────────────────┘
                    ▼
              calc_demo.exe
  • main.c 包含 calc.h，因为它要调用 calc_add、calc_div；
  • calc.c 也包含 calc.h，因为它要让编译器核对自己的定义；
  • calc.h 不包含任何 .c，也不包含 main.c；
  • 链接器只负责把 main.o 和 calc.o 拼起来，不关心谁包含了谁。

calc_div 的接口还顺手示范了一个重要的工程习惯：用返回值报告成功/失败，用指针参数带回结果。 这样调用者可以先判断 calc_div(...) == 0，再使用 quotient，不会在除零时拿到一个未定义的值。这个模式在考核里也会用到——但具体怎么用，由你设计。

小提醒：04 为了演示 NULL 包含了 <stddef.h>。考核题面如果只允许 stdio.h / stdlib.h，就改用这两个头文件里提供的 NULL（它们同样定义 NULL），或者直接判 out == 0，不要额外包含 <stddef.h>。示例工程不是考核模板，头文件范围以题面为准。

9.4 拆到多细才合适

对考核这种几百行的程序，4~6 个模块通常足够：

  • main.c：入口、状态循环、顶层调度；
  • 登录门禁模块：负责认证与尝试次数；
  • 个人信息模块：负责结构体、初始化、字段修改、展示；
  • 输入/菜单模块：负责显示、读入、清洗、错误提示；
  • 字符串工具模块：手写长度、比较、拷贝等（如果题面禁止库函数）。

再拆细就容易出现「一个函数一个文件」的过度设计；再拆粗就回到 800 行 main.c。判断标准不是行数，而是：这个文件能不能用一句话说清它的职责？ 说不清，就该拆；说得清但只有十行，也许该合并。

10. 核心概念八：菜单驱动程序——状态机、分派与输入清洗

10.1 菜单程序的五个部件

一个能用的菜单程序，通常由五部分组成：

  1. 状态（state）：现在是在登录、在主菜单、在某个子功能，还是该退出；
  2. 显示（view）：把当前可选的菜单项打印出来；
  3. 输入（input）：读一行、解析成数字、清洗非法字符；
  4. 分派（dispatch）：根据选择调用对应函数；
  5. 动作（action）：真正干活的函数，比如修改姓名、显示信息。

初学者常把五样东西全塞进 main 的 while 里，结果 main 越来越长，登录和菜单缠在一起，改一个选项要动十处。正确的做法是：main 只做状态循环和分派，具体动作都在函数里。

10.2 状态机：把「现在在哪」画出来

用文字画一个最简单的状态图：

[登录门禁] --成功--> [主菜单] --选择功能--> [功能处理] --完成--> 回到主菜单
     |                   |
     |                   +--选择退出--> [结束]
     +--失败达到上限------------------> [结束]

每个方框是一个状态，箭头是转移条件。把它写成代码，就是一个 while 加一个 switch，或者一个 enum 状态变量：

  • APP_LOGIN：显示登录提示，读输入，校验；成功则转到 APP_MENU，失败但未达上限则留在 APP_LOGIN 继续下一次，失败次数达到上限则转到 APP_EXIT；
  • APP_MENU：显示主菜单，读选择，分派到具体功能；选择退出则转到 APP_EXIT；
  • APP_EXIT：循环结束，打印结束语，返回 0。

这样做的好处是：登录只是状态机里的一个状态，不是套在菜单外面的另一层循环。 很多初学者写出「登录成功后再进入一个菜单循环，菜单退出后又回到登录」的迷宫，就是因为没有把状态理清。

10.3 函数分派：switch 是调度台，不是干活的地方

一个清晰的分派函数长这样（这是结构示意，不是完整程序）：

switch (choice) {
case 1:
    do_show(profile);
    break;
case 2:
    do_edit(profile);
    break;
case 0:
    running = 0;
    break;
default:
    printf("无效选项，请重新输入。\n");
    break;
}

每个 case 只做一件事：调用对应的动作函数。动作函数负责具体的输入、修改、打印；分派函数负责「选谁」。这样你加一个菜单项，只改菜单显示和 switch，不用动业务函数。

如果你学到练习 7，还可以把 switch 换成函数指针数组：把「选第几个函数」变成「查表」。语法形状是 void (*actions[])(void) = {action_one, action_two};，调用 actions[choice]();——前提是所有动作函数的签名完全一致。菜单如果需要传参，就把参数类型也写进函数指针类型，例如 void (*actions[])(AppData *)，调用时传 &app。它适合菜单项很多、或者需要动态换菜单的场景；初学阶段先把 switch 写扎实，函数指针作为挑战。

10.4 输入清洗：菜单程序的头号 bug 来源

先看一个经典事故（错误示范，不要照抄）：

int choice;
while (1) {
    printf("请选择：");
    scanf("%d", &choice);
    if (choice == 0) {
        break;
    }
    /* ... */
}

用户输入 abc，scanf("%d", &choice) 返回 0，choice 没被赋值，abc 还留在输入缓冲区里。下一轮循环，scanf 又看到 abc，又失败……屏幕上瞬间刷出成千上万行「请选择：」。这不是死循环，是输入缓冲区里的垃圾没被清走。

正确的输入清洗至少要做四件事：

  1. 读整行：用 fgets 或逐字符读到 \n，把一行完整取出来；
  2. 解析：只接受合法数字，拒绝空行、字母、多余字符；
  3. 清残留：如果一行太长，把剩余字符读掉，别留给下一轮；
  4. 处理 EOF：用户按 Ctrl+Z / Ctrl+D 时退出，不要空转。

配套 05_menu_skeleton.c 是一个完整可编译的骨架。它用一个「示例任务面板」演示结构，不含任何考核业务；你学的是骨架，不是把它的业务照搬。

/* 05_menu_skeleton.c —— 菜单驱动程序骨架：循环 + 分派 + 输入清洗
 * 编译：gcc -Wall -Wextra -std=c99 -g 05_menu_skeleton.c -o 05_menu_skeleton.exe
 * 说明：演示工程结构，不含任何考核业务；把 AppData 和示例动作换成你的业务即可。
 */
#include <stdio.h>

#define LINE_MAX 64

typedef struct {
    int task_count;
} AppData;

typedef enum {
    MENU_SHOW = 1,
    MENU_ADD = 2,
    MENU_CLEAR = 3,
    MENU_EXIT = 0
} MenuChoice;

/* 读一整行，丢掉换行；超长部分也一并丢弃，避免残留在缓冲区。
 * 返回 0 表示 EOF 且没有读到任何字符，返回 1 表示读到了一行。 */
static int read_line(char *buf, int cap)
{
    int ch;
    int len = 0;

    if (cap <= 0) {
        return 0;
    }
    while ((ch = getchar()) != '\n' && ch != EOF) {
        if (len < cap - 1) {
            buf[len++] = (char)ch;
        }
    }
    buf[len] = '\0';

    if (ch == EOF && len == 0) {
        return 0;
    }
    return 1;
}

/* 只接受十进制整数，前后可有空格/tab，其他字符一律判失败。
 * 菜单数字很小，这里用 1000000 的上限避免 int 溢出。 */
static int parse_int(const char *s, int *out)
{
    int i = 0;
    int sign = 1;
    long value = 0;

    while (s[i] == ' ' || s[i] == '\t') {
        i++;
    }
    if (s[i] == '+' || s[i] == '-') {
        if (s[i] == '-') {
            sign = -1;
        }
        i++;
    }
    if (s[i] < '0' || s[i] > '9') {
        return 0;
    }
    while (s[i] >= '0' && s[i] <= '9') {
        value = value * 10 + (s[i] - '0');
        if (value > 1000000L) {
            return 0;
        }
        i++;
    }
    while (s[i] == ' ' || s[i] == '\t') {
        i++;
    }
    if (s[i] != '\0') {
        return 0;
    }
    *out = (int)(sign * value);
    return 1;
}

static void show_menu(void)
{
    printf("\n===== 示例任务面板 =====\n");
    printf("1. 查看任务数量\n");
    printf("2. 添加一条示例任务\n");
    printf("3. 清空任务\n");
    printf("0. 退出\n");
}

static void do_show(const AppData *app)
{
    printf("当前任务数：%d\n", app->task_count);
}

static void do_add(AppData *app)
{
    app->task_count++;
    printf("已添加，当前任务数：%d\n", app->task_count);
}

static void do_clear(AppData *app)
{
    app->task_count = 0;
    printf("已清空。\n");
}

/* 返回 1 表示继续循环，返回 0 表示退出；菜单分派集中在这里 */
static int dispatch(AppData *app, int choice)
{
    switch (choice) {
    case MENU_SHOW:
        do_show(app);
        return 1;
    case MENU_ADD:
        do_add(app);
        return 1;
    case MENU_CLEAR:
        do_clear(app);
        return 1;
    case MENU_EXIT:
        return 0;
    default:
        printf("无效选项，请输入 0~3。\n");
        return 1;
    }
}

int main(void)
{
    AppData app = {0};
    char line[LINE_MAX];
    int choice;
    int running = 1;

    while (running) {
        show_menu();
        printf("请选择：");

        if (!read_line(line, (int)sizeof line)) {
            printf("\n输入结束，退出。\n");
            break;
        }
        if (!parse_int(line, &choice)) {
            printf("这不是有效数字，请重试。\n");
            continue;
        }
        running = dispatch(&app, choice);
    }

    printf("程序结束。\n");
    return 0;
}

这份骨架的关键点：

  • read_line 一次读一整行，超过 LINE_MAX 的字符被丢弃，不会留下残渣；
  • parse_int 自己解析十进制，不依赖 atoi，非法字符直接拒绝；
  • dispatch 只做分派，具体动作在 do_show、do_add、do_clear 里；
  • main 只有一个 while，一个 running 标志，没有嵌套菜单循环；
  • AppData * 和 const AppData * 演示了「改数据传指针、只读数据传 const 指针」。

把 AppData 换成你的个人信息结构体，把 do_show/do_add 换成你的业务函数，骨架就能用。但考核的登录、字段校验、5 次机会，必须由你按题面自己实现。

10.5 登录门禁应该怎么放

登录不是「在菜单里加一个选项」，而是菜单之前的门禁。结构上建议：

  • 用一个独立的登录函数或登录模块，输入账号/口令，返回「成功/失败/输入结束」；
  • 失败次数由调用者或登录模块按题面要求计数，达到上限就退出，不要无限重试；
  • 每次失败后清洗输入，避免残留字符影响下一次；
  • 登录成功后设置状态，再进入主菜单；
  • 登录失败提示不要泄露「是账号错还是口令错」这类细节（如果题面没有要求区分）；
  • 不要把登录循环嵌在菜单循环里，也不要在登录函数里直接打印主菜单。

状态机的好处在这里体现：登录和菜单是两个状态，各自只做自己的事。 你不需要写「登录成功后再 while 菜单，菜单退出再回到登录」这种绕来绕去的结构。

10.6 菜单程序的三个验收动作

写完菜单，至少手动做这三件事：

  1. 输入 abc、空行、超长字符串、999，看程序是否给出提示并回到菜单，而不是崩溃或刷屏；
  2. 输入 EOF（Ctrl+Z 回车 / Ctrl+D），看程序是否正常退出；
  3. 选择每个菜单项，走完「修改→查看→退出→重新运行」的完整路径，确认没有状态残留。

这三件事比多写十个功能更能决定考核成败。

11. 核心概念九：Makefile 入门——让机器记住「谁依赖谁」

11.1 为什么需要 Makefile

手动编译多文件，命令会越来越长：

gcc -Wall -Wextra -std=c99 -g main.c calc.c -o calc_demo.exe

每次改一个文件，所有 .c 都重新编译，所有 .o 都重新生成。程序小的时候无所谓，文件一多，等编译的时间足够你泡一杯茶。更麻烦的是：你很容易忘记把新加的 .c 加进命令，然后对着 undefined reference 发呆。

Makefile 的核心思想只有一句：只重建「比依赖旧」的目标。 它把「源文件、头文件、目标文件、可执行文件」之间的依赖关系写成规则，然后根据文件修改时间决定谁需要重编。这就是增量编译。

11.2 最小可用 Makefile

04_project_demo\Makefile 的完整内容：

CC = "C:/Program Files (x86)/mingw64/bin/gcc.exe"
CFLAGS = -Wall -Wextra -std=c99 -g
TARGET = calc_demo.exe
OBJS = main.o calc.o

all: $(TARGET)

$(TARGET): $(OBJS)
    $(CC) $(OBJS) -o $(TARGET)

main.o: main.c calc.h
    $(CC) $(CFLAGS) -c main.c -o main.o

calc.o: calc.c calc.h
    $(CC) $(CFLAGS) -c calc.c -o calc.o

.PHONY: all clean
clean:
    -del /Q $(OBJS) $(TARGET) 2>NUL

注意： 上面每个命令行开头都是一个真实的 Tab 字符，不是四个空格。Markdown 里看起来像缩进，复制到编辑器后请确认状态栏显示的是 Tab，不是 Spaces: 4。这是 Makefile 最著名的入门坑，后面 §14 还会再提。

11.3 逐行拆解

行 含义
CC = ... 编译器变量。路径带空格，所以用双引号包住；以后换编译器只改这一行
CFLAGS = ... 编译选项：警告、C99、调试信息
TARGET = calc_demo.exe 最终目标文件名
OBJS = main.o calc.o 所有目标文件，链接时要一起用
all: $(TARGET) 默认目标。直接运行 mingw32-make 时，从第一个目标开始
$(TARGET): $(OBJS) 可执行文件依赖两个 .o；任何一个比它新，就重新链接
$(CC) $(OBJS) -o $(TARGET) 链接命令，没有 -c
main.o: main.c calc.h main.o 依赖 main.c 和 calc.h；头文件变了也要重编
$(CC) $(CFLAGS) -c main.c -o main.o 编译命令，-c 表示只编译不链接
calc.o: calc.c calc.h 同理，calc.o 也依赖 calc.h
.PHONY: all clean 声明 all、clean 是「假目标」，不是真实文件
clean: 清理目标，删除 .o 和 .exe
-del /Q ... 2>NUL Windows 删除命令；开头的 - 表示忽略删除失败（文件本来就不存在时）

11.4 运行与观察增量编译

$make = "C:\Program Files (x86)\mingw64\bin\mingw32-make.exe"
Push-Location code\阶段八_多文件工程\04_project_demo

& $make                 # 第一次：编译 main.o、calc.o，再链接
.\calc_demo.exe
& $make                 # 第二次：应当显示 Nothing to be done for 'all'.
& $make clean           # 删除产物
Pop-Location

第一次运行，你应该看到三条命令：

gcc ... -c main.c -o main.o
gcc ... -c calc.c -o calc.o
gcc main.o calc.o -o calc_demo.exe

第二次运行，应该只看到：

mingw32-make: Nothing to be done for 'all'.

现在做两个实验：

  1. 只修改 calc.c（比如在某个函数里加一行注释保存），再 mingw32-make：应该只有 calc.o 重编，然后重新链接；
  2. 修改 calc.h（比如加一行注释保存），再 mingw32-make：main.o 和 calc.o 都应该重编，因为两个目标都把 calc.h 列为依赖。

这就是增量编译。它不神秘，只是依赖图 + 时间戳。

11.5 变量与自动变量

Makefile 的变量用 $(名字) 展开。除了自己定义的 CC、CFLAGS，Make 还提供自动变量：

  • $@：当前目标名；
  • $^：所有依赖名；
  • $<：第一个依赖名。

用自动变量可以把规则写得更通用：

%.o: %.c
    $(CC) $(CFLAGS) -c $< -o $@

这条模式规则的意思是：任何 .o 都可以由同名 .c 编译而来，命令是「编译第一个依赖，输出到目标」。初学阶段先把显式规则写清楚；读别人的 Makefile 时，认识 $@、$^、$< 就够了。

11.6 .PHONY 为什么重要

all 和 clean 不是真实文件。如果目录里恰好有一个叫 clean 的文件，Make 会认为 clean 目标已经「最新」，于是不执行清理命令。.PHONY 告诉 Make：「别管同名文件，这个目标每次都执行。」

同理，all 也是一个假目标，只是用来汇总最终产物。养成写 .PHONY 的习惯，能避免很多「为什么 make clean 不删文件」的怪事。

11.7 CMake：概念级对照

CMake 不是编译器，也不是 Make 的替代品；它是构建系统生成器。你写一份 CMakeLists.txt 描述「有哪些源文件、要生成什么目标」，CMake 根据你的平台生成 Makefile、Ninja 文件或 Visual Studio 工程，然后由底层的构建工具去执行。

一个概念示例（不是本阶段配套文件，只是让你看懂形状）：

cmake_minimum_required(VERSION 3.10)
project(calc_demo C)

set(CMAKE_C_STANDARD 99)
set(CMAKE_C_STANDARD_REQUIRED ON)

add_executable(calc_demo main.c calc.c)

它表达的意思和 Makefile 一样：用 main.c、calc.c 生成 calc_demo。但 CMake 会自动处理很多依赖细节，支持「out-of-source build」（在 build/ 目录里生成产物，不污染源码目录），也更容易跨平台。

对比项 Makefile CMake
本质 直接写构建规则 描述工程，生成构建规则
学习曲线 先懂目标/依赖/命令 先懂工程/目标/生成器
依赖管理 手写头文件依赖 通常自动分析

15. 安全与规范：本阶段三条铁律

15.1 三条铁律

  1. 一个外部符号只有一份定义。 头文件只放接口（声明、类型、宏），变量定义、函数体一律放 .c；共享变量用 extern 声明，定义只留一处。每次把东西写进 .h 之前，先问：「这会被几个 .c 包含？会不会变成多份？」
  2. 每个头文件都有守卫，每个 .c 都包含自己的头文件。 守卫防同一编译单元重复包含；包含自己的头文件让编译器核对声明与定义。私有函数一律 static，不导出、不写进头文件。
  3. 警告零容忍，输入必校验，指针必可证。 用 -Wall -Wextra -std=c99 编译；每个 scanf/读入都检查返回值；每个菜单输入都处理非法值、空行、超长和 EOF；每个指针出生时初始化，解引用前能说清它指向谁。

考核还额外有硬性要求：只允许 stdio.h / stdlib.h，至少一处指针，必须模块化，必须有注释。 前三条铁律是工程底线，后面四条是题面底线，一条都不能破。

15.3 注释规范

  • 文件头注释：文件名、模块职责、编译方式（可选）。让评审一眼知道这个文件干什么；
  • 函数注释：做什么、参数含义、返回值含义、失败时怎么办。尤其是返回状态码的函数，必须写清 0 和 -1 各代表什么；
  • 关键逻辑注释：为什么这样做，而不是逐行翻译代码。比如「登录失败只提示一次，避免泄露账号是否存在」；
  • 不要注释掉的死代码：提交前删掉，或至少标明「历史版本，不参与编译」；满屏注释掉的代码会拉低评审印象；
  • 注释跟着代码改：改了参数或返回值，注释必须同步，否则比没有注释更危险。

  • C 代码用 4 个空格缩进，左花括号风格全工程统一；一行一条语句；函数之间空一行；
  • 运算符两侧留空格，逗号后留空格；if (、for (、while ( 括号前留空格；
  • 一行不要过长，复杂表达式拆开；嵌套超过三层就考虑抽函数；

数据结构思路

  • 姓名字符串用固定长度字符数组，长度按题面上限留足 +1 给 '\0'；不要用变长数组；
  • 学号建议用字符串保存，而不是 int——前导零会丢，长度也可能超出整型范围；
  • 性别可以用 char 或 enum，但输入/输出要统一映射，别一会儿 'm' 一会儿 "男"；
  • 身高用 double，输出格式按题面（比如保留两位小数）；比较/修改时注意浮点误差，不要用 == 判断身高；
  • 登录口令如果题面要求保存，用固定字符数组；不要在屏幕上回显口令（如果题面要求隐藏输入，按题面做，不要自己发明）；
  • 所有字符串操作都要检查目标缓冲区容量，杜绝越界。

状态机与流程

建议把流程画成：

[登录] --成功--> [主菜单] --选择--> [功能] --完成--> 回主菜单
   |                  |
   |                  +--退出--> [结束]
   +--失败达上限 / EOF-------> [结束]

实现时用一个 while 和一个状态变量（enum 或 int），每个状态只做自己的事。登录失败按题面计数；成功进入菜单；菜单退出结束。不要写「登录成功后 while 菜单，菜单退出再回登录」的嵌套循环，除非题面明确要求。

指针计划（满足「至少一处」且不摆设）

  • 修改个人信息的函数接收 Profile *，在函数内通过 -> 改字段；
  • 只读展示接收 const Profile *，向调用者承诺不改；
  • 手写字符串比较接收 const char *，用指针遍历到 '\0'；
  • 如果使用传出参数（比如让函数返回状态、用指针带回结果），确保调用者传的是有效地址；
  • 每个指针定义时初始化（NULL 或有效地址），解引用前能说清它指向谁。

不要为了凑指针数量，把 int 改成 int * 再解引用。 评审一眼能看出是不是真需求；一处有意义的指针，胜过五处摆设。

输入与测试计划

  • 统一用「读整行 → 解析」的方式，不要混用 scanf("%d") 和 fgets；
