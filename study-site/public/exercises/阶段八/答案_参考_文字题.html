阶段八 参考答案（练习 3 · 纸上作业 + 练习 6 Makefile）参考答案

先自己做，再看答案。以下报错原文均来自本机 GCC 16.2.0（-Wall -Wextra -std=c99）实测， 路径和行号省略，只保留关键词；你的机器上路径会不同，关键词一样。

练习 3 编译链接推演（标准答案）

先记住三个阶段，四问全部挂在这张表上：

阶段 谁在工作 输入 → 输出 这一步能发现什么
编译 编译器（cc1） .c → .o 语法错、原型缺失、签名冲突、重复定义（同一编译单元内）
链接 链接器（ld） 多个 .o → .exe 函数/变量找不到（undefined reference）、多个同名全局符号（multiple definition）
运行 你的程序 .exe + 输入 → 输出 逻辑错、越界、空指针——编译器已经管不到了

① 每个 .c 单独 -c 的产物

gcc -Wall -Wextra -std=c99 -c main.c      # 产物 main.o
gcc -Wall -Wextra -std=c99 -c student.c   # 产物 student.o
gcc -Wall -Wextra -std=c99 -c util.c      # 产物 util.o

也可以一条命令一次生成三个：gcc -Wall -Wextra -std=c99 -c main.c student.c util.c。

三个 .o 里装的是：

  • 本文件函数的机器码；
  • 符号表：本文件定义了哪些符号（stu_total、stu_average、stu_print、main）， 引用了但还没找到哪些符号（main.o 里的 stu_total / stu_average / stu_print， student.o 里的 stu_print 不需要——它没调用打印）；
  • 重定位记录：等链接时再把「调用地址」填上。

关键点：-c 到汇编为止，不链接，所以 main.o 里允许存在「暂时找不到地址」的调用。

② 从 .o 到 exe 的链接命令

gcc -Wall -Wextra -std=c99 main.o student.o util.o -o score.exe

一条命令从源码直接到程序也可以（编译 + 链接一次完成，初学最常用）：

gcc -Wall -Wextra -std=c99 main.c student.c util.c -o score.exe

链接器做三件事：① 把三个 .o 的代码段拼在一起；② 给每个符号确定最终地址； ③ 把 main.o 里「待填」的调用地址补上。补不上就报 undefined reference。

本工程链接成功后运行，实测输出：

Alice     90
Bob       75
Cara      88
总分 = 253，平均分 = 84.33

③ main.c 里把 stu_average 拼成 stu_averge

分两种情况，报错发生在不同阶段，关键词也不同：

情况 A：拼错的名字没有原型（最常见）——编译期就拦下。

main.c:13:38: error: implicit declaration of function 'stu_averge'; did you mean 'stu_average'? [-Wimplicit-function-declaration]
main.c:12:36: warning: format '%f' expects argument of type 'double', but argument 3 has type 'int' [-Wformat=]

第一行是根因：编译器没见过 stu_averge，C99 不允许隐式声明。 第二行是连锁反应：隐式声明会「猜」返回 int，于是 %f 收到 int，格式不匹配。

关键词：implicit declaration of function、-Wimplicit-function-declaration。

情况 B：main.c 自己声明了一个不存在的函数，或者 student.c 里定义名拼错——编译期全过，链接期爆炸。

例如头文件里写的是 stu_average，main.c 却自己声明并调用了 stu_averge； 再比如 student.c 里把定义写成 stu_averge（头文件仍是正确的 stu_average）。 两种情况都会走到链接器，实测报：

undefined reference to `stu_average'
collect2.exe: error: ld returned 1 exit status

关键词：undefined reference to、ld returned 1 exit status、collect2.exe。

一句话：名字拼错 → 先在编译期问「你声明了吗」，声明了但没人实现 → 链接期问「它在哪」。

④ 头文件声明与 .c 定义签名不一致

情况 A：student.c 正确 #include "student.h"——编译器当场对质。

把定义改成 double stu_average(const Stu *list)（少一个 int n），实测：

student.c:12:8: error: conflicting types for 'stu_average'; have 'double(const Stu *)'
student.h:12:8: note: previous declaration of 'stu_average' with type 'double(const Stu *, int)'
student.c:14:9: error: 'n' undeclared (first use in this function)

第一行是签名冲突，第二行指出「之前在这里声明过」，第三行是函数体里继续用 n 引发的连锁错误。 关键词：conflicting types for、previous declaration of。

情况 B：student.c 忘了 #include "student.h"——编译器闭嘴，链接器也不查签名，最危险。

C 链接器只按符号名配对，不看参数表、不看返回类型。所以：

  • 如果漏 include 后签名恰好一致：能编、能链、能跑，只是你失去了编译器的核对（运气好而已）；
  • 如果签名不一致（比如返回类型 int vs double，或参数类型不同）：编译通过、链接通过、 运行时按错误的 ABI 解释参数和返回值，结果可能是乱码、可能是随机值、可能当场崩。 本机用一个最小例子复现过：main 声明 int compute(int a, int b)，compute.c 实际定义 int compute(int a)，链接零警告，运行 compute(21, 0) 输出 42——第二个参数被静默忽略。

关键词：没有报错。这正是它危险的原因：错误被推迟到运行期，还可能看起来「差不多对」。

结论：每个 .c 都必须 #include 自己的 .h。 头文件是模块对外的合同， .c 自查合同，编译器才能在你写错签名的那一刻拦住你。

阶段对照速查表（背下来）

你看到的关键词 阶段 常见原因 怎么修
implicit declaration of function 编译 没写原型 / 名字拼错 / 没 include 头文件 补原型、改拼写、补 #include
conflicting types for 编译 头文件与 .c 定义签名不一致 让定义与原型逐字一致（最好 .c include 自己的 .h）
redefinition of 编译 同一个 .c 里定义了两遍（头文件没守卫） 加 #ifndef 守卫
undefined reference to 链接 函数只有声明没有定义 / 少传一个 .o / 名字拼错 补实现、补 .o、改拼写
multiple definition of 链接 头文件里写了函数体，被两个 .c 包含 函数体搬回 .c，头文件只留原型
ld returned 1 exit status 链接 上面任一链接错误的收尾行 往上看第一条 undefined/multiple

常见错误（自查）

  • ❌ 只编译 main.c 就运行——undefined reference 一大片，因为另外两个 .c 根本没参与；
  • ❌ 头文件里写函数体——单个 .c 能过，两个 .c 一包含就 multiple definition；
  • ❌ 头文件里写 int count = 0;——同上，变量定义只能出现在一个 .c 里；
  • ❌ 以为 -Wall 能在链接期查参数——链接器不看参数表，签名错要靠「.c include 自己的 .h」防；
  • ❌ 改完 .h 只重编一个 .c——所有包含该头文件的 .c 都要重编（Makefile 的依赖就是干这个的）。

练习 6 Makefile 完整参考答案

完整 Makefile（命令行缩进必须是 TAB）

CC      = gcc
CFLAGS  = -Wall -Wextra -std=c99
TARGET  = grade.exe
OBJS    = main.o student.o
DEPS    = student.h

$(TARGET): $(OBJS)
    $(CC) $(CFLAGS) $(OBJS) -o $(TARGET)

%.o: %.c $(DEPS)
    $(CC) $(CFLAGS) -c $< -o $@

.PHONY: clean
clean:
    -del /Q $(OBJS) $(TARGET) 2>NUL

上面代码块里的缩进是真的 TAB。从网页复制到编辑器后，务必确认没有被换成空格—— 用 VSCode 打开，选中行首按 Tab 应显示一个箭头，而不是几个小点。

逐行解释

行 含义
CC = gcc 编译器命令。想换编译器只改这一行（如 CC = clang）。
CFLAGS = -Wall -Wextra -std=c99 编译选项。所有编译命令都用 $(CFLAGS)，统一改、统一生效。
TARGET = grade.exe 最终产物名。改名字只改这里。
OBJS = main.o student.o 参与链接的目标文件列表。
DEPS = student.h 公共头文件。单独拎出来，后面两条规则都要用。
$(TARGET): $(OBJS) 规则：grade.exe 依赖两个 .o。任何一个 .o 比 exe 新，就重新链接。
\t$(CC) $(CFLAGS) $(OBJS) -o $(TARGET) 链接命令（TAB 开头）。这里不再 -c，因为输入已经是 .o。
%.o: %.c $(DEPS) 模式规则：任意 X.o 依赖 X.c 和 student.h。% 是通配的「主干」。
\t$(CC) $(CFLAGS) -c $< -o $@ $< = 第一个依赖（X.c），$@ = 目标（X.o）。只编译不链接。
.PHONY: clean 声明 clean 是「假目标」，不是文件。
clean: 清理规则，没有依赖，所以每次调用都执行。
\t-del /Q $(OBJS) $(TARGET) 2>NUL Windows 删除命令；行首 - 让 make 忽略「文件不存在」的失败，2>NUL 吞掉错误提示。Linux 上改成 rm -f $(OBJS) $(TARGET)。

实测构建过程（本机 mingw32-make）

全量构建：

gcc -Wall -Wextra -std=c99 -c main.c -o main.o
gcc -Wall -Wextra -std=c99 -c student.c -o student.o
gcc -Wall -Wextra -std=c99 main.o student.o -o grade.exe

只改 student.c（哪怕只加一个空格）后再构建：

gcc -Wall -Wextra -std=c99 -c student.c -o student.o
gcc -Wall -Wextra -std=c99 main.o student.o -o grade.exe

只改 student.h 后再构建（两个 .c 都包含它，所以两个都重编）：

gcc -Wall -Wextra -std=c99 -c main.c -o main.o
gcc -Wall -Wextra -std=c99 -c student.c -o student.o
gcc -Wall -Wextra -std=c99 main.o student.o -o grade.exe

什么都没改再构建：

mingw32-make: 'grade.exe' is up to date.

执行 mingw32-make clean：

del /Q main.o student.o grade.exe 2>NUL

清理后目录里只剩 main.c、student.c、student.h、Makefile 四个文件。

为什么只改一个 .c 只重编一个？

三个词：目标、依赖、时间戳。

  • student.o 是目标，它的依赖是 student.c 和 student.h；
  • make 比较「目标文件的修改时间」和「依赖文件的修改时间」；
  • student.c 刚改过 → 比 student.o 新 → 规则触发，只重编 student.o；
  • main.c 没动 → main.o 比 main.c 新 → 跳过；
  • 但 grade.exe 依赖的两个 .o 里有一个变新了 → 链接这一步必须重跑。

注意：make 只看时间戳，不看内容。touch 一下文件（内容没变）也会触发重编； 反过来，如果系统时间乱了、或者从压缩包解压导致时间戳全一样，make 可能误判「不用重编」， 这时 mingw32-make clean 后重来最稳。

.PHONY 到底防什么？

如果目录里恰好有一个名叫 clean 的文件，而 clean 规则又没有依赖：

  • 没有 .PHONY：make 发现 clean 已存在且没有依赖比它新 → 认为「clean 是最新的」→ 什么都不做；
  • 有 .PHONY：make 知道 clean 不是文件，每次都执行命令。

同理，all、run、test 这类不对应真实文件的目标都应该进 .PHONY。

$@、$<、$^ 速记

自动变量 含义 在 %.o: %.c student.h 里
$@ 目标名 main.o
$< 第一个依赖 main.c
$^ 所有依赖（去重） main.c student.h

本题的编译命令只需要 $< 和 $@；如果把头文件也写进命令（没必要），才会用到 $^。

改 CFLAGS 的坑（练习 6 第 5 问）

把 CFLAGS 改成 -std=c89 后直接 mingw32-make，很可能什么都不重编—— 因为 Makefile 本身不在依赖列表里，make 不知道「编译选项变了」。 正确做法：先 mingw32-make clean，再构建。

另外，本练习的代码恰好全是 C89 兼容写法（声明都在块首、注释都用 /* */）， 所以 -std=c89 实测仍然零警告通过。想亲眼看到 C99 特性报错，可以临时做两件事之一：

  • 把 for (i = 0; ...) 改成 for (int i = 0; ...)，实测报： error: 'for' loop initial declarations are only allowed in C99 or C11 mode；
  • 在文件里加一行 // 注释，实测报： error: C++ style comments are not allowed in ISO C90。

看完记得改回 -std=c99 并 clean 重建。

练习 6 五问速答

  1. 构建/清理：mingw32-make 全量构建，mingw32-make clean 清理； make 没装时用 mingw32-make（本机即如此）。
  2. 只改 student.c：只重编 student.o，然后重新链接；main.o 不动。
  3. 为什么：目标 student.o 的依赖 student.c 时间戳更新，规则被触发；其余目标都还「新」。
  4. .PHONY：让 clean 永远执行，不受同名文件干扰。
  5. 改 CFLAGS：Makefile 不是依赖，改选项不会自动重编；先 clean 再构建。
