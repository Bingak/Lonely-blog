2. 场景引入：50 人的成绩表，和一次“关机归零”

阶段四你写过成绩统计。那时数组多半是这样开的：

#define MAX_STUDENTS 50
struct Student scores[MAX_STUDENTS];

50 个人时它工作得很好。直到实验室招新，老师轻描淡写地说：“这届人多，按 200 人准备。”你回去把 50 改成 200，重新编译，发现栈空间开始吃紧；如果明年变成 2000 人，这个办法就彻底不体面了。更尴尬的是：程序运行时你才知道实际人数，而数组长度在编译前就定死了。“运行时才知道要多少”，是数组天生的盲区。

第二个故事更常见。你写的菜单程序跑得好好的，输入数据、查询、统计，一切正确。你关掉窗口，再打开，屏幕干干净净——刚才那些人、那些成绩，像没来过一样。程序的内存随进程结束一起消失，这不是 bug，是内存的本分。你要让数据跨过“关机”这道门，就得把它写到磁盘上。

于是本阶段要补上两种能力：

  • 动态内存：程序跑起来以后，按实际人数向系统借一块地，函数返回了地还在，直到你亲手还。
  • 文件 IO：把内存里的记录变成字节写到磁盘，下一次启动再读回来，重新变成结构体。

但这两样东西都不是免费的。借地不还会泄漏，还了以后还拿旧钥匙开门是悬垂指针，同一把钥匙还两次是 double free；文件打开了不关，缓冲区里的数据可能还在路上。你之前学的指针、结构体、字符串，在这两章里会第一次真正“合体”。

3. 核心概念一：栈与堆——两种“活着”的方式

3.1 栈：函数借你用的折叠桌

你到目前为止用的局部变量、局部数组，几乎都住在栈（stack）上。函数被调用时，系统给它划出一小块栈帧，参数、局部变量、返回地址都放在里面；函数一返回，这块栈帧就被收回。

这解释了两件旧事：

  1. 阶段三说的“形参是实参的复印件”，复印件就放在栈帧里；
  2. 阶段五说的“不要返回局部变量的地址”，因为函数一返回，那张折叠桌就被收走了，你拿到的门牌号指向一块已经失效的区域。

栈的优点非常突出：分配和回收只是挪一下栈指针，快得几乎没有成本；缺点是小，而且生命周期被函数调用绑死。在 Windows 桌面上栈通常有几 MB，看上去很多，但递归一深、局部数组一大，照样会栈溢出。到了 51 单片机，栈空间更是按字节抠着用。

补充一句：C99 确实有变长数组（VLA），int a[n]; 在某些编译器上能过。但它仍然住在栈上，大小受栈限制，函数一返回就没了，不能当“可长期保存、可增长”的容器。工程上真正的动态容器还是用堆。

3.2 堆：去仓库签字借一张桌子

堆（heap）是进程运行时的一块内存池。你不直接给它起变量名，而是调用 malloc 向它“借”指定字节数，它返回这块地的首地址。你把这个地址存进指针，之后通过指针读写。

堆的寿命和函数无关：只要没 free，函数返回了它还在，别的函数也能用；反过来，只要你不还，它会一直占着，直到进程结束。它通常比栈大，但也不是无限的；分配和释放需要管理元数据，速度比栈慢，而且长时间反复借还不同大小的块，会产生碎片。

3.4 生命周期对比：函数走后，谁还活着

int *make_numbers(int n)
{
    int local[3] = {1, 2, 3};
    /* return local; 错误：函数返回后 local 的栈帧就没了 */

    int *heap = malloc((size_t)n * sizeof *heap);
    if (heap == NULL) {
        return NULL;
    }
    for (int i = 0; i < n; i++) {
        heap[i] = i;
    }
    return heap;       /* 合法：堆块还活着，所有权交给调用者 */
}

local 是栈上的折叠桌，函数一走就收；heap 是仓库里签了字的桌子，函数走了还在，但签字的人（调用者）现在有责任去还。阶段五那道“不能返回局部变量地址”的警告，和这里“可以返回堆指针”的区别，不在于指针类型，而在于它指向的东西还活不活。

4. 核心概念二：malloc——向堆借地，先查 NULL

4.1 它只认字节，不认类型

malloc 的原型在 <stdlib.h>：

void *malloc(size_t size);

参数是字节数，返回值是那块地的首地址；失败返回 NULL。它不知道你要装 int 还是 Student，所以返回 void *。在 C 里，void * 可以隐式转换成任何对象指针，不需要强转：

int n = 5;
int *a = malloc((size_t)n * sizeof *a);   /* 借 n 个 int 的空间 */
if (a == NULL) {                          /* 借不到就必须处理 */
    fprintf(stderr, "内存分配失败\n");
    return 1;
}
for (int i = 0; i < n; i++) {
    a[i] = i * i;
}
printf("a[4] = %d\n", a[4]);
free(a);                                  /* 用完归还 */
a = NULL;                                 /* 旧钥匙作废 */

sizeof *a 读作“a 指向的那个东西的大小”。它的好处是：类型改了，这行不用改。如果写成 sizeof(int)，将来把 int 换成 double 或结构体，很容易漏改。

4.2 为什么必须检查 NULL

桌面电脑内存大，malloc 失败不常见，所以很多人养成“不检查”的坏习惯。但失败一旦发生，后面就是拿空指针去解引用：

int *a = malloc(10 * sizeof *a);
a[0] = 1;        /* 如果 a == NULL，这里通常直接崩 */

在单片机和长时间运行的程序里，内存不足是真实会发生的事件，不是理论概率。正确姿势是：每次分配后立刻检查，失败就停在那条错误路径上，不要继续写。 这不是“多写一行”，而是把崩溃点从不可预测的远处，提前到你能解释的当下。

4.3 sizeof 陷阱：sizeof p 不是 sizeof *p

配套 01_malloc_basics.c 会打印：

printf("sizeof(a)=%zu, sizeof(*a)=%zu\n", sizeof a, sizeof *a);

在 64 位 MinGW 上，指针是 8 字节，int 是 4 字节，所以你会看到 8 和 4。两个经典错误由此而来：

int *p = malloc(n * sizeof p);   /* 借了 n 个“指针大小”，不是 n 个 int */
int *q = malloc(sizeof q);       /* 只借了 8 字节，却想当 n 个 int 用 */

第一行可能只是浪费空间；第二行则是严重不足，写几个元素就踩到堆的边界。统一写成 malloc((size_t)n * sizeof *p)，让“元素个数 × 每个元素大小”这句话直接落在代码里。

还有两个细节：

  • 字符串要多留一格：char *s = malloc(len + 1);，最后放 '\0'。这是阶段四的旧账，在堆上同样要还。
  • malloc(0) 的行为由实现决定：可能返回 NULL，也可能返回一个不能解引用的唯一地址。不要依赖它，需要零长度就单独处理。

malloc 还有一个必须记住的性格：它不清零。新借来的地里面是上一次使用留下的垃圾，读到什么都合法，但都不是你要的。需要零初始化，下一节的 calloc 就是干这个的。

5. 核心概念三：free 与“谁分配谁释放”

5.1 free 做三件事，但不做第四件

free(void *p) 把 p 指向的堆块还给分配器。它做的是：

  1. 把这块地标记为空闲，之后可能被再次借出；
  2. 更新分配器的记账信息；
  3. 接受 NULL（free(NULL) 是合法的空操作）。

它不做的是：把你手里的指针自动改成 NULL。调用 free(p) 之后，p 里仍然保存着那个旧地址，这就是下一节悬垂指针的入口。所以纪律是：

free(p);
p = NULL;        /* 自己把纸条擦干净 */

还要记住三个“不能 free”：

  • 不能 free 栈上的数组：int a[10]; free(a); 是灾难；
  • 不能 free 字符串字面量：char *s = "UPRE"; free(s); 也是灾难；
  • 不能 free 堆块内部的地址：free(p + 1) 不是“还一半”，而是非法。

free 只认分配器当初返回的那个地址（或 NULL）。

5.2 “谁分配谁释放”不是口号，是接口契约

一块堆内存从生到死，必须有一个明确的负责人。最稳妥的默认规则是：谁调用 malloc/calloc/realloc 申请，谁负责在合适的时机 free。 但函数之间可以转移所有权，转移时必须写清楚。

场景 谁负责释放 接口注释应该怎么写
函数内部临时申请、函数内用完 函数自己 /* 内部临时缓冲，返回前释放 */
函数申请并返回给调用者 调用者 /* 返回新数组；成功由调用者 free，失败返回 NULL */
函数只借用调用者的指针 调用者 /* 借用，不取得所有权，不 free */
容器负责释放内部元素 容器的销毁函数 /* destroy 会释放容器及其中的每个元素 */

看一个所有权转移的例子：

int *make_numbers(int n)
{
    int *a = malloc((size_t)n * sizeof *a);
    if (a == NULL) {
        return NULL;                    /* 失败：没有东西需要释放 */
    }
    for (int i = 0; i < n; i++) {
        a[i] = i;
    }
    return a;                           /* 所有权交给调用者 */
}

int main(void)
{
    int *nums = make_numbers(5);
    if (nums != NULL) {
        printf("%d\n", nums[3]);
        free(nums);                     /* 谁接过了所有权，谁负责还 */
        nums = NULL;
    }
    return 0;
}

这段代码能编译运行。它最重要的不是语法，而是那条注释：读函数的人不用猜这块内存该由谁还。 你以后写多文件工程，头文件里的函数声明旁边就该有这类说明。

5.3 有多个出口时，别漏掉 free

函数里一旦出现提前 return，最容易漏掉清理。比如一个函数先申请 buf，随后某一步校验失败就直接 return 0，那条分支上的 free(buf) 很容易被忘记。每一条提前返回的路，都要先还再走。

当资源变多（内存、文件、锁），可以考虑“单一清理出口”的写法：用 goto cleanup 统一收尾，或者在每个失败分支显式释放。对现在的你，先守住一条：画一遍函数所有 return 路径，逐条问“这块地还了吗”。

6. 核心概念四：calloc——带零初始化的租约

calloc 也声明在 <stdlib.h>：

void *calloc(size_t count, size_t size);

它申请 count * size 字节，并把每个字节初始化为 0；失败返回 NULL。和 malloc 比，它多了“清零”这一步，参数也拆成了“几个”和“每个多大”。

最适合它的场景是计数器、标志数组、需要从 0 开始累加的表。比如统计 0~9 每个数字出现了几次：

int *count = calloc(10, sizeof *count);
if (count == NULL) {
    fprintf(stderr, "calloc 失败\n");
    return 1;
}

int samples[] = {3, 7, 7, 1, 9, 7};
for (size_t i = 0; i < sizeof samples / sizeof samples[0]; i++) {
    count[samples[i]]++;
}
printf("7 出现了 %d 次，0 出现了 %d 次\n", count[7], count[0]);

free(count);
count = NULL;

如果这里换成 malloc，你必须自己写循环清零；忘了清，count[7]++ 就是在垃圾值上加一，结果完全不可信。calloc 把“清零”变成分配契约的一部分，读代码的人一眼就知道初始状态。

两点提醒：

  • calloc 不是“更高级的 malloc”，它只是多做了清零；不需要初值且数据马上会被覆盖时，malloc 就够了。
  • 对常见的整数、字符、结构体，全字节 0 通常就得到你要的 0；但不要把它当成所有类型在所有平台上“必然表示零值”的绝对保证。当前阶段用它来管整数计数和普通记录，足够稳妥。

7. 核心概念五：realloc——扩容的三种结局

数组一旦借定大小，就不能原地变长。需要更多格子时，用 realloc 申请一块新的、更大的空间：

void *realloc(void *ptr, size_t new_size);

它有三种结局，必须全背下来：

结局 返回值 原内存块 你要做什么
原地扩展 原地址（可能相同） 仍然有效，扩大 直接使用新大小
搬到新家 新地址 旧块已被释放，内容已复制 用新指针替换旧指针
失败 NULL 仍然有效，内容未动 保留旧指针，处理错误

第三种是最容易出人命的：realloc 失败时不会释放旧块。 如果你直接写：

data = realloc(data, newcap * sizeof *data);
if (data == NULL) {
    /* 旧块已经丢了地址，泄漏！ */
}

失败的一瞬间，realloc 返回 NULL，你把它赋给了 data，原来那块地的唯一地址被覆盖，既不能再用也不能再 free。正确写法永远是“先接住，再赋值”：

int *tmp = realloc(data, newcap * sizeof *data);
if (tmp == NULL) {
    /* 失败：data 和旧内容都还在，可以继续用或安全退出 */
    fprintf(stderr, "扩容失败\n");
} else {
    data = tmp;          /* 成功后才覆盖原指针 */
    cap = newcap;
}

配套 02_dynamic_array.c 会把每次扩容前后的地址打印出来。你可能会看到地址一直不变（原地扩），也可能看到它搬家（复制到新地址）。两种都正常，取决于分配器后面有没有连续空位。扩容成功后，所有指向旧数组元素的指针都作废，不要再拿 &data[1] 这类旧地址去用。

另外：

  • realloc(NULL, n) 等价于 malloc(n)；
  • realloc(p, 0) 的行为在标准里比较微妙，实践中不要用它来“释放”，要释放就 free(p)；
  • 新扩出来的部分不会自动清零，里面是未初始化的字节；需要零就自己写 0；
  • 计算 newcap * sizeof *data 前，最好确认乘法不会溢出。初学阶段容量很小，但把这个检查写进扩容函数，是工程习惯。

8. 核心概念六：悬垂指针与 double free

8.1 悬垂指针：钥匙还在，房子已经退了

free(p) 只把堆块还给分配器，不会通知所有保存了同一地址的指针。看这段：

int *p = malloc(sizeof *p);
if (p == NULL) {
    return 1;
}
*p = 42;

int *q = p;      /* q 和 p 拿着同一张门牌号 */
free(p);         /* 房子退了 */
p = NULL;        /* p 这张纸条擦干净了 */
/* 但 q 仍保存旧地址，q 现在是悬垂指针；*q 是未定义行为，绝对不要读或写 */

悬垂指针的可怕之处在于：它可能暂时还能读出旧值。堆块被回收后，内容不会立刻被擦掉，分配器也可能暂时没把这块地借给别人。于是你运行一次，打印出 42，以为没事；下一次同样的代码却崩溃，或者悄悄改坏了别人的数据。“这次跑对了”不是证据，未定义行为从来不保证结果。

典型来源：

  • free 之后继续用原指针；
  • 一个函数 free 了，另一个函数还保存着别名；
  • 返回一个指向已释放堆块的指针；
  • realloc 搬家后，还拿着旧地址。

8.2 double free：同一把钥匙还两次

free(p);
free(p);      /* 未定义行为，常见结果是堆损坏或崩溃 */

如果 free 后立刻 p = NULL，第二次 free(NULL) 是安全的；但如果还有别名 q，free(q) 依然会造成 double free。所以“free 后置 NULL”只能保护当前这个指针，不能保护所有副本。真正可靠的办法是明确所有权：一块内存只有一个负责人，负责人释放后，其他人不再持有它。

8.3 越界写：破坏发生在“隔壁”

堆块本身不知道自己的长度。malloc(5 * sizeof *a) 只给你 5 个 int 的地盘，但 a[5] = 1 依然能编译、能运行——它写到了第 6 格，也就是分配器元数据或下一块别人的数据上。这种破坏最阴险的地方是现场不报错：可能过了半小时，在一次毫不相干的 free 或 malloc 时才崩溃，真正的肇事行早已过去。

防御手段很朴素：循环边界永远用 < len；用户输入的下标先检查 0 <= i && i < len；动态数组先 reserve 再写。ASan 能报 heap-buffer-overflow，但没有 ASan 时，C 不会替你拦。

8.4 配套示例为什么只“讲”不“引爆”

03_leak_and_dangle.c 是安全观察版：它演示泄漏、演示 free 后置 NULL 的纪律，也打印悬垂指针保存的旧地址，但不会真的解引用已释放的内存。这不是胆小，而是教学纪律：未定义行为不应作为课堂实验。你要在纸上推演“如果此时写 *q 会发生什么”，而不是让程序替你撞一次墙。

9. 核心概念七：内存泄漏的三种典型形态

内存泄漏指：堆块已经不可能再被使用，但也没有被 free。程序占用的内存只会增长，不会回落。它不会立刻报错，所以比崩溃更阴险。

9.1 丢了唯一地址

int *p = malloc(100 * sizeof *p);
p = malloc(200 * sizeof *p);     /* 第一块地的地址被覆盖，永远找不回来 */

这不是“分配失败”，而是“主动失忆”。任何覆盖指针变量之前，都要先问：旧块还了吗？

9.2 提前返回，跳过清理

int work(const int *src, int n)
{
    if (n <= 0) {
        return 0;
    }
    int *buf = malloc((size_t)n * sizeof *buf);
    if (buf == NULL) {
        return 0;
    }
    if (src == NULL) {
        return 0;                /* 漏了 free(buf)，这条错误路径泄漏 */
    }
    for (int i = 0; i < n; i++) {
        buf[i] = src[i];
    }
    free(buf);
    return 1;
}

错误路径往往是最少被测试的路径。函数每多一个 return，就多一条需要核对的释放路线。

9.3 只释放外壳，没释放内容

结构体数组或“指针的数组”里，容器本身释放了，元素指向的堆块却没释放：

for (int i = 0; i < n; i++) {
    free(items[i].name);         /* 先释放每个元素内部的内存 */
}
free(items);                     /* 再释放装元素的容器 */
items = NULL;

顺序不能反：先释放内层，再释放外层。反过来，外层一没，内层地址就丢了。

还有一类变体：realloc 失败时直接用返回值覆盖原指针，导致旧块泄漏——这就是 §7 的“先接住再赋值”。

关于“程序退出操作系统会回收”：这句话在桌面短程序里成立，但在服务器、守护进程、单片机和 RTOS 里完全不成立。一个跑几个月的程序，每次泄漏几十字节，最后也会把内存吃光。学习阶段就要把“退出会回收”当成“这不是我的免责条款”。

10. 核心概念八：检查内存——Valgrind 思路与 Windows 的替代手段

10.1 Valgrind 到底在做什么

Valgrind 是 Linux 上常用的动态分析工具。它的核心思路并不神秘：拦截每一次分配和释放，记录地址、大小、调用栈；程序结束时，看哪些分配没有对应的释放。

gcc -g -Wall -Wextra -std=c99 leak.c -o leak
valgrind --leak-check=full --show-leak-kinds=all ./leak

它会报 definitely lost（确定丢失）、indirectly lost（间接丢失）等分类，并给出分配点的调用栈。它还能抓越界读写、使用未初始化值、释放后访问。关键不是背命令，而是理解它的账本：分配一条，释放一条，最后对账。

10.2 Windows 没有 Valgrind，先试 AddressSanitizer

原生 Windows 上没有 Valgrind（除非你用 WSL 或 Linux 虚拟机）。GCC/Clang 提供 AddressSanitizer（ASan），编译时加：

& "C:\Program Files (x86)\mingw64\bin\gcc.exe" -std=c99 -g -fsanitize=address 01_malloc_basics.c -o asan_demo.exe

但 MinGW 的支持情况必须现场确认，不能想当然。本资料所用的是 MinGW-Builds 的 GCC 16.2.0，实测链接阶段报：

ld.exe: cannot find -lasan: No such file or directory

这说明这套 MinGW 没有附带 ASan 运行库，命令用不了。不同发行版、不同安装方式可能不一样：有的 MinGW-w64 带 libasan，有的没有；Visual Studio 也可以安装 AddressSanitizer 组件。先探测，再决定——如果链接报 cannot find -lasan，就接受现实，转入手工审计，不要为了一个工具重装整条工具链浪费两天。

10.3 手工审计：没有工具也能对账

Valgrind 的“拦截—记录—对账”思路，用纸和调试器也能做：

  1. 列出所有分配点：在工程里搜 malloc、calloc、realloc，每个都编号；
  2. 画分配/释放对照表：记下分配函数、地址变量、字节数、由谁释放、在哪些 return 路径上释放；
  3. 看所有权转移：函数返回的堆指针，调用者有没有接住并最终 free；容器销毁时有没有释放内部元素；
  4. 在每个 return 前检查：尤其是错误分支；
  5. 用调试器盯三个值：指针本身、*p、p == NULL 的状态；free 后立刻置 NULL，再单步确认没有别处使用；
  6. 重复运行测试：同一功能反复加载/退出几十次，观察内存占用是否持续上涨。

一个实用的调试习惯是：在分配和释放处临时打印地址与位置，例如 alloc p=000001F0... at load()、free p=000001F0... at destroy()。地址每次运行会变，但在同一次运行里可以一一配对；如果最后有 alloc 没有对应的 free，账就对不上。正式提交前把调试打印删掉即可。

10.4 工具不是免死金牌

ASan 能抓很多越界和 use-after-free，但它不能证明“逻辑上该释放的都在正确时机释放了”；Valgrind 能报泄漏，但也不理解你的业务所有权。工具负责发现症状，你负责设计所有权。 本阶段真正要建立的是后者。

11. 核心概念九：动态数组——长度、容量与扩容

11.1 两个数字，别混

动态数组的核心不是“用了 malloc”，而是把两个概念分开：

  • 长度 len：现在真正存了多少个元素，用户能访问的范围是 [0, len)；
  • 容量 cap：这块地一共能装多少个元素，cap >= len，多出来的格子暂时空着。

数组满了（len == cap）才扩容。扩容不是每次加一格，而是按倍数增长（常见是翻倍）。这样从 0 加到 n，总复制量是 1+2+4+…+n，均摊到每次追加是常数级；如果每次只加一格，总复制量会变成平方级，数据一多就慢得明显。

追加第几个元素 扩容前 cap 扩容后 cap 需要搬的元素数
1 0 2 0
3 2 4 2
5 4 8 4
9 8 16 8

11.2 完整可运行示例

下面这段代码就是 02_dynamic_array.c 的核心形态。它会在每次扩容前后打印地址，让你亲眼看到 realloc 是原地扩还是搬家：

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *data = NULL;       /* 动态数组的起点 */
    size_t len = 0;         /* 已经用了多少格 */
    size_t cap = 0;         /* 一共借了多少格 */
    int seed[] = {10, 20, 30, 40, 50, 60};

    for (size_t i = 0; i < sizeof seed / sizeof seed[0]; i++) {
        if (len == cap) {                       /* 坐满了，申请更大的桌子 */
            if (cap > ((size_t)-1) / 2) {
                fprintf(stderr, "capacity overflow\n");
                free(data);
                return 1;
            }
            size_t newcap = (cap == 0) ? 2 : cap * 2;
            if (newcap > ((size_t)-1) / sizeof *data) {
                fprintf(stderr, "size overflow\n");
                free(data);
                return 1;
            }
            printf("before grow: len=%zu cap=%zu data=%p\n",
                   len, cap, (void *)data);
            int *tmp = realloc(data, newcap * sizeof *data);
            if (tmp == NULL) {
                fprintf(stderr, "realloc failed; old block is still valid\n");
                free(data);
                return 1;
            }
            data = tmp;                         /* 先接住，再改原指针 */
            cap = newcap;
            printf("after  grow: len=%zu cap=%zu data=%p\n",
                   len, cap, (void *)data);
        }
        data[len++] = seed[i];
    }

    printf("len=%zu cap=%zu ->", len, cap);
    for (size_t i = 0; i < len; i++) {
        printf(" %d", data[i]);
    }
    printf("\n");

    free(data);
    data = NULL;
    return 0;
}

运行后你会看到容量从 0 到 2、4、8，而长度逐次增加。打印地址只是观察，不要用地址是否变化来写逻辑；真正的逻辑永远是 len == cap 时扩容。

11.3 动态数组的三条纪律

  1. 先用 len 保证不越界，再写 data[len++]；不要把 cap 当长度遍历，空着的格子是未初始化内容；
  2. 扩容成功后重新获取元素地址；realloc 可能搬家，旧的 int *p = &data[1] 已经失效；
  3. 数组销毁时只 free 一次外层；如果元素内部还有指针，要先逐个释放内层，再释放外层。

12. 核心概念十：文件 IO 全套——把内存写成字节

12.1 FILE 是什么

C 标准库用 FILE * 表示一个流。它可能是磁盘文件、键盘（stdin）、屏幕（stdout）或错误输出（stderr）。你不需要知道 FILE 内部长什么样，只需要通过 fopen 打开、用读写函数操作、用 fclose 关闭。

流有位置：读或写会推进位置；流有缓冲区：标准库可能先在内存里攒一批数据，再一次性写盘。理解这两点，后面的 fclose 和 \r\n 才有落脚点。

12.2 fopen 的六种文本模式

FILE *fopen(const char *path, const char *mode);
模式 读/写 文件不存在 已有内容 初始位置
"r" 只读 失败，返回 NULL 保留 开头
"w" 只写 创建 清空 开头
"a" 只写（追加） 创建 保留 末尾
"r+" 读/写 失败，返回 NULL 保留 开头
"w+" 读/写 创建 清空 开头
"a+" 读/写 创建 保留 写总在末尾；读起点由实现决定

几个容易踩的点：

  • "w" 只要打开成功就立即截断文件，哪怕你一个字都没写。拿它做“先读后写”会先把自己的数据清空。
  • "a" 的写入永远追加到末尾，不能覆盖前面的内容。
  • "r+" 不会创建文件，路径打错就返回 NULL。
  • 更新模式（带 +）在读写之间切换时，位置规则较细；初学阶段最稳的做法是写完 fclose，再重新 fopen 读，或者用 fflush/fseek 明确调整位置。不要在同一条流上随意又读又写。

12.3 打开必须检查

FILE *fp = fopen("students.csv", "r");
if (fp == NULL) {
    perror("students.csv");      /* 打印失败原因，便于定位 */
    return 1;
}

fopen 失败的原因很多：路径不对、权限不够、文件被占用、父目录不存在。不检查就 fgets，等于拿空指针去读。 另外注意相对路径是相对于程序当前工作目录，不是相对于 .c 文件所在目录。VSCode 运行、终端运行、双击 exe 的当前目录可能不同，文件“明明在”却打不开时，先打印当前路径或用绝对路径验证。

12.4 fprintf / fscanf 的返回值

fprintf 成功返回写入的字符数，失败返回负数：

if (fprintf(fp, "%d,%s,%.2f\n", id, name, score) < 0) {
    fprintf(stderr, "写入失败\n");
}

fscanf 返回成功赋值的项数；如果还没读到任何项就遇到输入结束或错误，返回 EOF。最常见的坑是这个循环：

int x = 0;
while (fscanf(fp, "%d", &x) != EOF) {   /* 错误示范：遇到字母可能死循环 */
    printf("%d\n", x);                  /* 匹配失败时仍会进循环，x 还是旧值 */
}

如果文件里出现字母，%d 匹配失败，fscanf 返回 0，文件位置没有前进；下一轮还是同一个字母，还是返回 0，永远等不到 EOF。正确写法是明确期望的项数：

int x = 0;
while (fscanf(fp, "%d", &x) == 1) {
    printf("%d\n", x);                  /* 读到一个整数才进入循环 */
}

或者更稳妥地：用 fgets 读一整行，再用 sscanf 解析这一行。这样每轮一定消费掉一行，不会卡死，也更容易报出“第几行格式错”。

12.5 fgets 逐行读：文件版的“安全输入”

char *fgets(char *s, int size, FILE *stream);

它最多读 size - 1 个字符，自动补 '\0'；遇到换行就停下，并且把换行也存进去（如果装得下）。返回 NULL 表示读到文件末尾或发生错误。

char line[256];
while (fgets(line, sizeof line, fp) != NULL) {
    size_t n = strlen(line);
    if (n > 0 && line[n - 1] == '\n') {
        line[n - 1] = '\0';          /* 去掉行尾换行 */
    }
    /* 现在 line 是一整行（除非它比 255 字符还长） */
}

三件事要记：

  1. fgets 不会因为空格停下，所以能读带空格的姓名或整句话；
  2. 换行会被保留，统计字符数或打印时要么去掉，要么把它算进去；
  3. 如果一行比缓冲区长，fgets 会分多次读完这一行，你的“按行解析”会把它当成多行。缓冲区宁可开大一些，并在格式错误时报出行号。

12.6 把写、关、开、读串起来

下面这个完整程序先写两行文本、关闭，再重新打开逐行读回，统计行数和字符数：

#include <stdio.h>
#include <string.h>

int main(void)
{
    const char *path = "demo_io.txt";
    FILE *fp = fopen(path, "w");
    if (fp == NULL) {
        perror(path);
        return 1;
    }
    if (fprintf(fp, "UPRE 2026\n") < 0 ||
        fprintf(fp, "dynamic memory & file io\n") < 0) {
        fprintf(stderr, "write failed\n");
        fclose(fp);
        return 1;
    }
    if (fclose(fp) != 0) {                     /* 关文件才会把缓冲区刷出去 */
        perror("fclose");
        return 1;
    }

    fp = fopen(path, "r");
    if (fp == NULL) {
        perror(path);
        return 1;
    }
    char line[128];
    size_t lines = 0;
    size_t chars = 0;
    while (fgets(line, sizeof line, fp) != NULL) {
        size_t n = strlen(line);
        lines++;
        chars += n;
        if (n > 0 && line[n - 1] == '\n') {
            line[n - 1] = '\0';                /* 去掉读进来的换行 */
        }
        printf("line %zu: %s\n", lines, line);
    }
    if (ferror(fp)) {
        fprintf(stderr, "read error\n");
        fclose(fp);
        return 1;
    }
    if (fclose(fp) != 0) {
        perror("fclose");
        return 1;
    }
    printf("lines=%zu chars=%zu\n", lines, chars);
    return 0;
}

这段程序能编译运行，输出两行内容和 lines=2 chars=35。注意 35 是读进来的字符数（含两个 \n），而磁盘上的文件是 37 字节——多出的 2 字节就是 Windows 文本模式悄悄写下的两个 \r。这就引出了下一节。

12.7 fclose：不是礼貌，是数据落盘的一部分

fclose(fp) 做两件事：把输出缓冲区里还没写的数据刷到文件，然后释放流。成功返回 0，失败返回 EOF。

为什么必须关：

  • 缓冲区可能还握着最后一批数据，程序异常结束（崩溃、被杀）时可能丢；
  • 关闭失败可能意味着磁盘写满、U 盘拔出，必须报告；
  • 长期不关会耗尽文件句柄，后续 fopen 失败。

每一条 return 路径都要关文件，包括写失败、解析失败的分支。上面示例在每次失败时都先 fclose 再返回；写文件时还检查了 fprintf 的返回值。fflush(fp) 可以强制刷新输出缓冲区，但它不能代替 fclose，也不要在输入流上随意调用。

12.8 文本模式 vs 二进制模式：Windows 的 \r\n 坑

打开模式后面加 b 就是二进制模式："rb"、"wb"、"ab"、"r+b" 等。

行为 文本模式（如 "w"） 二进制模式（如 "wb"）
写 '\n' Windows 上实际写成 \r\n（0D 0A） 原样写 0A
读 \r\n 自动翻译成 '\n' 原样读两个字节
ftell 的位置 不保证是字节偏移 通常是字节偏移
适合 CSV、日志、人可读文本 结构体、图片、自定义二进制格式

这就是为什么本程序写了两行文本，磁盘上是 37 字节，而 chars 统计到 35。 文本模式在帮你把 C 的 \n 翻译成 Windows 习惯的换行；读回来时再翻译回去。你在 C 源码里看不到 \r，但文件里确实有。

两个坑：

  1. 二进制数据用文本模式打开：数据中的 0A 可能被当成换行翻译，0D 0A 可能被改写，字节数就对不上，结构体直接错位；
  2. 文本数据用二进制模式打开：fgets 读到的行尾会带着 \r，解析 CSV 的最后一个字段时可能多一个看不见的字符。要么用文本模式，要么在读入后手动去掉 \r。

模式不是“随便选一个”，而是写和读必须成对一致。用 "wb" 写，就用 "rb" 读；用 "w" 写，就用 "r" 读。

12.9 fwrite / fread：整块字节的搬运

size_t fwrite(const void *ptr, size_t size, size_t nmemb, FILE *stream);
size_t fread(void *ptr, size_t size, size_t nmemb, FILE *stream);

size 是单个元素的字节数，nmemb 是元素个数，返回值是成功搬运的完整元素个数，不是字节数。写入结构体数组：

size_t written = fwrite(students, sizeof *students, count, fp);
if (written != count) {
    /* 写少了：磁盘满、流错误，或参数算错 */
}

读回：

Student buf[100];
size_t got = fread(buf, sizeof *buf, 100, fp);
if (ferror(fp)) {
    /* 读错误 */
}
/* got 是真正读到的完整记录数；可能因为文件尾而小于 100 */

feof(fp) 只有在尝试读越过文件末尾之后才为真，不能拿它当“下一项存在吗”的预判。循环读时看 fread/fgets 的返回值，循环结束后再检查 ferror。另外，fread 不会给字符数据补 '\0'，读完要自己补。

13. 核心概念十一：结构体记录持久化——CSV 与二进制

13.1 先把“一条记录”定下来

#define NAME_MAX 32

typedef struct {
    int id;
    char name[NAME_MAX];
    double score;
} Student;

这个结构体里没有指针，所以可以安全地按值复制、按数组保存。注意 name 是定长字符数组，不是 char *：如果把 char * 直接 fwrite 到文件，写进去的是地址数值，下一次运行地址早就不成立了。持久化只能存数据本身，不能存进程内的指针。

13.2 CSV 方案：一行一条，人也能读

CSV 的本质是“用分隔符把字段排成一行”。写：

fprintf(fp, "id,name,score\n");
for (size_t i = 0; i < n; i++) {
    if (fprintf(fp, "%d,%s,%.2f\n",
                a[i].id, a[i].name, a[i].score) < 0) {
        fclose(fp);                  /* 写失败也要关闭文件 */
        return 0;                    /* 由调用者知道保存失败 */
    }
}

读的时候用 fgets 拿整行，再用 sscanf 按格式解析：

while (fgets(line, sizeof line, fp) != NULL) {
    Student s;
    if (sscanf(line, "%d,%31[^,],%lf",
               &s.id, s.name, &s.score) != 3) {
        /* 这一行格式不对：报错、跳过，或停止 */
        continue;
    }
    /* 把 s 放进数组 */
}

%31[^,] 的意思是“最多读 31 个非逗号字符”，31 来自 NAME_MAX - 1，必须给 '\0' 留一格。CSV 的优点是：记事本能打开、出问题能肉眼查、不同程序之间容易交换、字段顺序清楚。缺点是：姓名里有逗号就会把字段切错；浮点数有精度和格式差异；每次都要解析，数据量大时慢。姓名里可能出现逗号时，要么禁止，要么实现引号转义——这已经超出本阶段，先在设计时规避。

13.3 二进制方案：把结构体原样写进去

/* 写：一条记录占 sizeof(Student) 字节 */
size_t written = fwrite(a, sizeof *a, n, fp);
if (written != n) {
    /* 处理写入失败 */
}

/* 读：最多读 cap 条，got 是实际条数 */
size_t got = fread(buf, sizeof *buf, cap, fp);
if (ferror(fp)) {
    /* 处理读错误 */
}

二进制方案的优点是紧凑、快、读回来就是内存里的结构体，不需要解析。缺点是不透明：文本编辑器打开是乱码；而且它把当前编译器的结构体布局当成了文件格式。Student 在 64 位 MinGW 上很可能是 48 字节：int 4 字节、name 32 字节，为了对齐 double 中间还会插入填充字节，最后才是 8 字节的 double。你写的字段明明只有 44 字节，sizeof 却是 48，多出来的就是填充。

13.4 两种方案的正面对比

维度 CSV 文本 二进制 fwrite/fread
可读性 记事本可读，便于排错 乱码，需要工具或程序
体积 有字段名、分隔符和换行开销；短记录反而可能更小 没有字段名和分隔符，但结构体填充、定长字段可能抵消优势
速度 需要格式化和解析 整块搬运，快
跨平台 较好，注意换行和编码 差：端序、填充、类型宽度、ABI 都可能变
字段变更 加列/改顺序要改解析；旧文件可兼容 极脆弱：结构体大小一变，后续记录全部错位
名字含分隔符 逗号会破坏格式 无此问题（但长度固定）
适合 配置、少量记录、需要人看的数据 本机缓存、性能敏感、格式完全受控的数据

本教程验证时用 3 条短记录做过对比：CSV 文件 65 字节，二进制文件 144 字节，sizeof(Student) 为 48。二进制不一定更小——短记录加上结构体填充，反而可能比文本更占地方。不要背“二进制一定省空间”的结论，要在自己的数据上打印文件大小和 sizeof 对比。配套 05_struct_file_db.c 就是干这件事的：CSV 和二进制各存一遍、各读一遍，比较文件大小与读回一致性。

13.5 版本兼容：字段一改，旧文件就可能读不了

这是持久化最容易被低估的问题。假设第一版 Student 是 id + name + score，第二版在中间加了一个 int age：

  • CSV：旧文件的行少一个字段，sscanf 返回值变成 2 或 3，你可以选择“缺省补 0”，也可以报错；
  • 二进制：旧文件按旧 sizeof 排列，新程序按新 sizeof 读，从第二条记录开始全部错位，读出来的 id 可能是别人的名字片段。

工程上的对策：

  1. 二进制文件写头部：魔数（如 "STU1"）、版本号、记录条数，读时先验证再决定怎么解析；
  2. 字段变更就升版本，并提供迁移逻辑，而不是假设旧文件“应该还能读”；
  3. 不要直接把含指针的结构体写进文件，写它指向的内容；
  4. 写结构体前先清零，避免把填充字节里的旧数据也写进文件；
  5. 对需要跨机器交换的数据，优先 CSV，或者逐字段写定宽整数并约定字节序。

这些不是“以后再说”的高级话题。你只要把程序交给别人一次，或者自己隔一周再打开旧数据，就会遇到。

17. 安全与规范：本阶段三条铁律

  1. 一块堆内存只有一个负责人，所有权必须在接口上写明。 谁申请谁释放是默认规则；要转移所有权，就在注释和函数命名里说清楚。容器销毁时，先释放内部元素，再释放容器。
  2. 借之前查 NULL，换之前先接住，还之后不再碰。 malloc/calloc/realloc 每次检查失败；realloc 永远用临时指针接住；free 后立刻置 NULL，并且不再通过任何别名访问。一次分配对应一次释放，所有 return 路径都要对账。
  3. 文件操作必须闭环：开必查、读写必验、关必查，模式成对。 fopen 检查 NULL；fprintf 看是否小于 0；fscanf 看赋值项数；fgets/fread 看返回值；每条路径都 fclose 并检查结果；文本文件用文本模式，二进制文件用二进制模式。

把这三条写进你的代码模板。以后做驱动、RTOS 队列、协议缓冲，换的只是资源类型，纪律一模一样。

衔接预告（阶段十：51 单片机 C 语言预备）： 下一阶段你要面对一个没有宽裕内存、没有通用操作系统、没有 Valgrind 的世界——51 单片机的 RAM 常常只有几十到几百字节，栈和全局变量先占掉一大块，函数调用深一点都心疼。这就是为什么嵌入式里通常要慎用 malloc：

  • 堆管理器本身要占 RAM，块头和对齐还会降低利用率；
  • 反复分配不同大小的块会产生碎片，设备连续跑几个月，碎片可能把内存切成许多无法使用的小洞；
  • 分配耗时不确定，可能破坏实时性；
  • 分配失败时，设备没有“弹个错误框”的余地，必须有确定的降级路径；
  • 很多 51 工程根本没有通用的文件系统，持久化靠 EEPROM/Flash，而不是 fopen。

所以嵌入式的常用手段是静态分配、固定大小缓冲、内存池、环形队列：在编译期或启动时就把上限算清楚，运行期只借固定尺寸的块，不还来还去。阶段十的 sbit、特殊功能寄存器、volatile、位运算点灯和数码管段码，都会在这个“资源必须可预测”的前提下展开。

但这不意味着本阶段白学。RTOS 的队列、驱动里的收发缓冲、协议栈里的包管理，仍然到处是“谁申请、谁释放、什么时候失效”的问题。你现在练的所有权、容量、生命周期和错误路径，正是从桌面 C 走向嵌入式 C 的桥。
